# 空中格式与链路状态机

本文定义 zlrs 的空中协议。身份与密钥见 [02-security.md](02-security.md)，
线程与射频栈见 [01-system.md](01-system.md) 第 7 节，系统级取舍见
[01-system.md](01-system.md)。

## 1. 物理层已经给了什么

设计帧之前先明确哪些不用自己做——LR2021 通过 RAC 已经提供：

| 能力 | 硬件提供 | 我们要做的 |
| --- | --- | --- |
| 前导码 | 是（`agc_pbl_len`） | 取值见 5.3 |
| 同步字 | 是（FLRC，3 个槽，每个 2 或 4 字节） | 用它做第一级过滤，见 1.1 |
| CRC | 是（`SetFlrcPacketParams`） | **不需要自己加 CRC** |
| 长度字段 | 是（变长包格式） | 不需要自己带长度 |

结论：**帧里不要重复携带 CRC 和长度**，这两样是射频链路层的活。

### 1.1 配对过滤用同步字

**帧里不放 `pair_id`，过滤交给射频同步字。**

同步字是硬件匹配的：不匹配的包在射频层就被丢弃，MCU 根本不会被唤醒。

| 槽 | 值 | 用途 |
| --- | --- | --- |
| 1 | `KDF(pair_key, "zlrs/sync/control")[:4]` | sub-GHz 控制链路 |
| 2 | `KDF(pair_key, "zlrs/sync/data")[:4]` | 2.4G 数据链路 |
| 3 | 公开常量 | 配对模式 |

这带来一个很强的性质：**配对之后，本机在物理层就听不到其它配对的流量**，
不消耗任何 MCU 时间或空口字节。

同步字固定用 4 字节（32 位），这样才装得下派生值。速率档不编码进同步字——
两端本来就必须处在同一速率才能通信。

代价：切换频段时要连同步字一起重配（本来就要改频率，顺带做掉）；
配对改变后要重算一次。

## 2. 帧格式

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `header` | 1 B | 高 6 位 = 类型（64 种），低 2 位 = 标志 |
| `seq` | 2 B | 会话内递增，防重放、用于分片重组 |
| `payload` | 0..N B | 类型相关 |
| `tag` | 0 或 4 B | HMAC 截断，覆盖 header + seq + payload |
| `crc` | 硬件追加 | 由射频链路层生成与校验 |

`tag` 是否存在、载荷是否加密，由 **profile 决定，不由标志位决定**。否则攻击者
只要清掉标志位就能把认证降级掉。

### 2.1 header 标志位

| 位 | 名称 | 含义 |
| --- | --- | --- |
| 0 | `MORE` | 分片未结束 |
| 1 | `ACK_REQ` | 请求对端确认 |

### 2.2 包类型

6 位类型空间共 64 种，当前占用 9 种。

| 值 | 类型 | 方向 | 说明 |
| --- | --- | --- | --- |
| 0 | `RC` | TX 到 RX | 遥控通道 |
| 1 | `TLM` | RX 到 TX | 遥测 |
| 2 | `DATA_UP` | TX 到 RX | 透传数据 |
| 3 | `DATA_DOWN` | RX 到 TX | 透传数据 |
| 4 | `ACK` | 双向 | 透传确认（ARQ profile 用） |
| 5 | `BEACON` | TX 到 RX | 会话建立、信道/跳频同步、profile 声明 |
| 6 | `PAIR_REQ` | TX 到 RX | 配对 |
| 7 | `PAIR_RESP` | RX 到 TX | 配对 |
| 8 | `PAIR_CFM` | TX 到 RX | 配对 |
| 9–63 | 保留 | — | — |

### 2.3 安全 profile

| profile | tag | 加密 | 用途 |
| --- | --- | --- | --- |
| `P0` | 无 | 无 | 仅调试，不可用于实际飞行 |
| `P1` | 4 B | 无 | **默认** |
| `P2` | 4 B | AES-CTR | 认证加密；MAC 覆盖密文（encrypt-then-MAC） |

- `tag` = **HMAC-SHA256 截断到 4 B**，覆盖 `header` + `seq` + `payload`。
- 选 HMAC-SHA256 是为了让身份层**只用 SHA-256 一个原语**：PBKDF2、HKDF、MAC
  全部落在同一族函数上，不必为 P1 引入 AES。P2 才需要 AES。
- profile 由 **TX 在 `BEACON` 里声明，RX 跟随**。TX 是链路的权威方。

### 2.4 控制帧载荷与速率档

| 项 | 默认 | 其它档位 |
| --- | --- | --- |
| 控制帧率 | **150 Hz** | 100 / 50 Hz |
| 通道数 | 16 | — |
| 每通道位宽 | 11 位 | — |
| `RC` payload | 22 B | — |

`RC` 帧的载荷**直接搬 CRSF 的 22 字节通道数据**（16 通道 × 11 位打包），
RX 侧重建 CRSF 的帧头与 CRC8。只搬不解——解包重编要选位宽（省不下多少）、
引入转换损耗，而 CRSF 的 11 位编码本身就是个稳定标准。

150 Hz、22 B 载荷下，27 字节帧在 0.975 Mbps 上约 222 us，占 6.67 ms 周期的
3.3%，余量充足。250 Hz 是 5.6%，500 Hz 是 11%。

### 2.5 分片规则

- `MORE` 置位表示后面还有分片。
- 接收端**严格按 `seq` 顺序重组**。
- 出现缺口、或超过 20 ms 未收齐，**丢弃整段**。
- 不做乱序重组：显式分片头（`frag_idx` + `frag_total`）每包要多付 2 B，
  代价大于收益。

### 2.6 空口开销核算

以 22 字节载荷、FLRC 1.3 Mbps（有效 0.975 Mbps）为例：

| 组成 | 字节 | 空口（估算） |
| --- | --- | --- |
| header + seq + payload | 25 | 约 205 us |
| 加 4 B tag（P1/P2） | 29 | 约 238 us |
| 前导码与同步字 | — | 再加几十 us |

tag 的代价约 16%，前导码与同步字是固定开销，速率越高占比越大。
这些数字按有效速率线性折算，属于量级估算。

### 2.7 链路质量与诊断

**不另建诊断通道，复用 CRSF 既有的字段。** CRSF 自带一个链路统计帧
（`0x14` LINK_STATISTICS），字段正好覆盖我们需要的：

| CRSF 字段 | 我们的来源 |
| --- | --- |
| 上行 RSSI | RX 测得的接收强度 |
| 上行 LQ | RX 侧"收到 / 应收"的成功率 |
| 上行 SNR | RX 测得 |
| 下行 RSSI / LQ / SNR | TX 侧自己测 |
| RF 模式 | 当前速率档 |

于是有两个生成点：

- **RX 到飞控**：用自己测到的上行质量组装
- **TX 到遥控器**：下行质量自己测，上行质量从遥测里取

这意味着**遥测回程里必须带上 RX 侧的链路质量**（LQ、RSSI、SNR、当前档位）。
这是 `TLM` 帧要承载的内容之一。

速率自适应的判据（见 4.5）用的是同一组指标，不另外采一套。

具体字节布局以 CRSF 规范为准，不在这里重述。

数据链路的溢出与丢弃字节数没有现成的 CRSF 字段承载，不上报。

## 3. 链路状态机

### 3.1 两条链路的关系

控制链路（sub-GHz）与数据链路（2.4G）各跑一份同样的状态机，互相独立。
系统级的「在线」由控制链路决定：控制链路在即系统在线；数据链路掉线只降吞吐。

### 3.2 状态

| 状态 | 含义 |
| --- | --- |
| `UNCONFIGURED` | 没有 `root_key`，什么都不做 |
| `UNPAIRED` | 有 `root_key`，但没有配对记录 |
| `PAIRING` | 用户按下按键，正在配对 |
| `SEARCHING` | 有配对记录，正在尝试建立连接 |
| `CONNECTED` | 已建立连接，正常收发 |

`UNCONFIGURED` 与 `UNPAIRED` 的区别只影响对外提示，行为上都是「不参与」。

### 3.3 TX 侧转移

| 起点 | 事件 | 终点 | 动作 |
| --- | --- | --- | --- |
| `UNCONFIGURED` | 写入 `root_key` | `UNPAIRED` | 生成并保存 `dev_id` |
| `UNPAIRED` | 长按按键 | `PAIRING` | 降功率、切配对同步字、周期发 `PAIR_REQ` |
| `PAIRING` | 配对成功 | `SEARCHING` | 记录对端 `dev_id`、恢复功率、切常态同步字 |
| `PAIRING` | 超时 30 s | `UNPAIRED` | 恢复功率与同步字 |
| `SEARCHING` | 周期发 `BEACON`，收到对端遥测即认为已连上 | `CONNECTED` | 进入常态收发 |
| `CONNECTED` | 250 ms 收不到任何有效包 | `SEARCHING` | 继续发 `BEACON` |

### 3.4 RX 侧转移

与 TX 对称，差别是 RX 不主动发 `BEACON`，只监听：

| 起点 | 事件 | 终点 | 动作 |
| --- | --- | --- | --- |
| `UNCONFIGURED` | 写入 `root_key` | `UNPAIRED` | 生成并保存 `dev_id` |
| `UNPAIRED` | 长按按键 | `PAIRING` | 切配对同步字、监听 `PAIR_REQ` |
| `PAIRING` | 配对成功 | `SEARCHING` | 记录对端 `dev_id`、切常态同步字 |
| `SEARCHING` | 收到 `BEACON`、锁定会话 | `CONNECTED` | 按 profile 配好射频，进入常态 |
| `CONNECTED` | 100 ms 收不到有效包 | `SEARCHING` | 输出失控保护值 |

失控保护是 `CONNECTED` 之外的一个**输出行为**，不是链路状态：`SEARCHING` 期间
RX 必须持续输出预设的失控值给飞控，不能中断。

失控值由 **TX 侧配置、配对时下发给 RX 存本地**。默认「油门 0、其余通道中位」，
可配置为「保持最后有效值」。

### 3.5 会话建立（零回程握手）

TX 周期性在固定信道上发 `BEACON`，携带三样东西：

| 内容 | 作用 |
| --- | --- |
| `nonce_t` | 本次会话的随机数 |
| 信道 / 跳频信息 | RX 据此对齐；见第 5 节 |
| profile | 速率档、tag 开关、加密开关 |

RX 收到后：

1. 校验 `nonce_t` 不是已处理过的旧值（拒绝重放）。
2. 算 `session_key = KDF(pair_key, "zlrs/session", nonce_t)`。
3. 按 profile 重配射频（速率、同步字）。
4. 进入 `CONNECTED`，序列号从 0 起，此后收发一律用 `session_key`。

**不需要任何回程确认。** 理由：

- 密钥本身不参与协商，`nonce_t` 是公开值，单向广播足够。
- 「TX 是否知道 RX 收到了」本来就靠后续遥测判断，加一次显式 ACK 并不改变这一点。
- RX 比 TX 晚开机时，等下一个 `BEACON` 即可。

`nonce_t` 在 TX 每次重启或重建链路时重新随机生成，因此每次会话的密钥都不同。
RX 记住最近接受的 `nonce_t`，重复的丢弃。

`BEACON` 周期：控制链路 **每秒一次**，数据链路 **每 2 秒一次**。

**两条链路各自发自己的 `BEACON`，各自建立会话。** 数据链路不依赖控制链路，
这样"一条断了不影响另一条"才真正成立。两条链路用的是同一套代码，只是参数不同。

已知弱点：攻击者若能重放一个旧 `BEACON`，可把 RX 拉到错误的会话密钥上，
造成一个 `BEACON` 周期长度的中断。下一帧真实 `BEACON` 到达即恢复。
判定为可接受；要消除需要给 `BEACON` 加单调的会话序号。

### 3.6 定时器

两条链路的严格程度不同：

| 项 | 控制链路 | 数据链路 |
| --- | --- | --- |
| 配对窗口 | 30 s | 30 s |
| 分片重组 | 20 ms | 20 ms |
| 失联判定 | RX 失控保护 100 ms / TX 250 ms | **无判定**，只统计"最近收到过什么"，超时约 5 s 且超时不触发任何动作 |
| `BEACON` 周期 | 1 s | 2 s |

控制链路严格，因为它承载操控，必须知道对方在不在。数据链路宽松，因为它是
尽力而为的辅助通道，"断了也无所谓"。

**全部按时间定义，不按包数**——这样换帧率不需要改参数。

## 4. 超帧与速率档

### 4.1 固定超帧

**每个控制周期形状完全相同。** 动态分配时隙能省下约 3% 的切换开销，代价是
延迟上限不可算、出问题难定位；[01-system.md](01-system.md) 第 1 节那条
"确定性延迟、故障可预测可检测"的要求更值这 3%。

一个周期（150 Hz，6.67 ms）的形状：

| 段 | 内容 | 约计 |
| --- | --- | --- |
| 1 | sub-GHz：TX 发 `RC` 帧 | 238 us |
| 2 | sub-GHz：切收，RX 发遥测帧（**必须回应**） | 91 + 238 us |
| 3 | 切到 2.4G | — |
| 4 | 2.4G：数据窗口，前半 TX 到 RX，后半 RX 到 TX | 约 5.7 ms |
| 5 | 切回 sub-GHz | — |

控制链路加频段切换合计约 924 us，占周期的 14%。这里的数字是 1.3 Mbps 档、
29 字节帧的粗估，参考 [01-system.md](01-system.md) 第 4 节。

调度用 RAC 的优先级机制表达：

| 链路 | RAC 优先级 | 调度方式 |
| --- | --- | --- |
| 控制链路 | `RAC_HIGH_PRIORITY` | 超帧由应用排序，RAC 侧 `ASAP` |
| 数据链路 | `RAC_MEDIUM_PRIORITY` | 控制链路空出来的时隙，`ASAP` |

时隙顺序由应用保证：RAC 的排期粒度是毫秒，而超帧时隙是亚毫秒级，
所以应用按超帧推进、逐个提交事务，RAC 只负责尽快执行。

### 4.2 遥测窗口

**RX 必须回应**，即使这一周期没有任何遥测数据，也要发一个最小的空帧
（`header` + `seq` + `tag`，约 7 B，空口约 57 us）。

理由：TX 靠"这个周期收到东西了吗"判断链路存活。如果 RX 只在有遥测时才发，
TX 就无法区分"链路断了"和"暂时没数据"，失联判定会失效。

### 4.3 数据窗口

数据窗口**固定对半分**：前半 TX 到 RX，后半 RX 到 TX。时序最可预测；
单向流量时会浪费一半，但数据链路本来就是尽力而为，接受这个代价。

**不发空帧。** 数据链路不做严格的失联判定，见 3.6。

数据链路的默认 profile 是 **best-effort**：裸字节流，缓冲满即丢，附溢出计数。
理由：透传的典型用途（MAVLink 遥测流）对延迟敏感、对丢包容忍，而且上层协议
往往自带重传。ARQ 作为可切换档保留。

ARQ 档的实现要点（见 `include/zlrs/link/link.h` 与 `lib/link/link.c`）：

- 载荷头 2 字节是数据序号，接收端按它去重、按序投递；确认用**累计 ACK**
  （ACK 帧带"已按序收到哪个序号"）
- 发送窗口 4 帧、超时 30 ms 重传、最多 6 次。窗口是"从队首开始连续的若干帧"，
  只有收到 ACK 才把字节从队列里提交，所以重传不需要额外缓存
- 重传用尽：这一段计成丢弃（可见计数），窗口清空、序号重开，并**发一次重同步**
  让接收端把半截消息作废——否则后面的数据会被拼到带洞的流上
- 会话里的第一帧必须从序号 0 开始：宁可丢一段，也不能把半截流错位投递给上层

**帧长动态**，上限为 `min(255, 当前速率档下半个窗口能装下的字节数)`。
每帧都要付固定开销（前导码 + 同步字），短帧的吞吐只有长帧的四分之一左右：

| 帧长 | 单帧空口（含前导/同步） | 单向吞吐 |
| --- | --- | --- |
| 29 B | 约 287 us | 约 43 kB/s |
| 128 B | 约 700 us | 约 110 kB/s |
| 255 B | 约 1100 us | 约 175 kB/s |

（2.6 Mbps 档、每周期单向 2.85 ms 的粗估。）

但**一帧必须在窗口内发完，不能跨窗口**，否则时序会乱。所以低速档下长帧反而
装不下，上限必须跟着速率档走：

| 速率档 | 半窗口能装下 |
| --- | --- |
| 2.6 Mbps | 约 695 B |
| 1.3 Mbps | 约 348 B |
| 0.65 Mbps | 约 174 B |
| 0.325 Mbps | 约 87 B |

### 4.4 速率自适应

**两条链路都自适应，但目标函数不同：**

| 链路 | 目标 | 质量退化时的行为 |
| --- | --- | --- |
| 控制链路 | 距离与稳定性 | **降速率档**换灵敏度，接受帧率下降 |
| 数据链路 | 帧率与吞吐 | 优先保住速率与帧率，不为距离而降速 |

所以速率档不能只是一个速率值——降速会让单包空口变长，150 Hz 的周期可能装不下。
**档位是「频段 + 速率 + 帧率」的组合**。

数据链路的速率档上限由**配置的串口波特率**推导：用户设 115200，链路就要能扛住
约 11.5 kB/s；设 921600，就是约 92 kB/s。配置工具负责校验这个目标在当前配置下
是否可达。这样用户不需要凭空估"峰值带宽"。

### 4.5 自适应判据

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 主判据 | 滑动窗口成功率 | 链路质量的地面真相 |
| 辅助 | RSSI | 领先指标，能提前预警 |
| 滞回 | 降档与升档阈值分开 | 同一个阈值会导致两档之间反复横跳 |
| 不对称 | 降档看约 1 s，升档看约 5 s | 链路要断了要快降，升档是试探性的 |
| 升档 | 先升上去试一小段，不行就退回 | 比"条件满足直接升"稳 |

单看成功率反应慢，单看 RSSI 受多径影响大，所以两者结合。

## 5. 跳频策略

**采用逐包跳频（每包换一个频点）**：索引由 `fhss_seed` 派生的频点表决定，
TX 在 `BEACON` 里携带索引与相位，RX 按同一张表与之锁步。

这样同时买到抗干扰能力、与其它 zlrs 链路的共存能力，以及法规跳频条款所需的
信道数与驻留时间。代价是收发时序必须按「每包一个时隙」建模，而不是「一直开着
收」：RX 在特定时刻打开特定频点。

### 5.1 逐包跳频的前提

四个前提，缺一不可：

| 前提 | 来源 |
| --- | --- |
| 共同的频点表 | `fhss_seed` 派生（两端各自算） |
| 共同的时隙长度 | 速率档决定 |
| 共同的索引与相位 | `BEACON` 携带，周期性重同步 |
| 时钟漂移的处理 | 靠 `BEACON` 周期重同步，晶振精度决定重同步频率 |

最后一条是最难的地方：两端晶振有偏差，跑一段时间后 RX 就会"踩空"。
所以 `BEACON` 不只是建链用，**它同时是周期性的时间基准**。

### 5.2 法规约束

跳频参数由目标地区决定：

- FCC 15.247 的跳频条款要求 ≥50 个信道、单信道驻留 ≤400 ms、各信道等概率使用。
  逐包跳频与慢跳频都满足；固定信道不满足，只能走非跳频的功率限制条款。
- ETSI EN 300 220 的某些子频段有占空比限制（1% / 10%），这会直接限制
  控制帧率与透传可用的时隙比例。
- 2.4G ISM 无跳频要求，宽松得多。

所以需要一层**地区配置**，把信道表、功率、占空比上限参数化。
板级 dtsi 已经按这个思路分频段给功率表（`tx-power-cfg-lf` / `tx-power-cfg-hf`），
地区配置沿用同一模式即可。

### 5.3 前导码与同步字

- 同步字固定 **4 字节**。
- 前导码在 datasheet 给出的最小值之上留余量。
