# User experience: the button and the status LED

The device has no screen, so all the user can touch is **one button** and **one RGB LED** (the
WS2812 on the RP2350-Zero). This document fixes what those two mean. Ports and modes:
[07-firmware](07-firmware.md); protocol: [08-protocol](08-protocol.md).

The goal: **you can tell what state the device is in without a computer**, and never by colour
alone — colour and cadence both carry information.

## Button

The button has exactly one action:

| Action | Condition | Result |
| --- | --- | --- |
| Long press | hold for 1 s or more (`CONFIG_ZLRS_APP_PAIR_HOLD_MS`) | start pairing (the handshake) |

There is no short press: releasing before 1 s does nothing. Pairing has consequences, so it is
worth holding a moment longer and cannot happen by accident. Re-binding is a long press too: the
new pairing record replaces the old one; there is no separate unpair action.

The button is standard equipment: the carrier board has one (SW1, GP12 to ground with an
internal pull-up); on the prototype a jumper wire from GP12 to GND stands in for it. A board
without the alias simply has no button and pairing comes from the management tool.

**Configuration does not use the button**: management mode is entered by a command the tool sends on
the management CDC (see [09-security](09-security.md) 9), with no physical action at all.

One press triggers pairing once; a new press needs a release in between. TX and RX share the
same button semantics.

## Status LED

One pixel cannot say much, so the LED uses both **colour and cadence** with fixed priorities: at
any moment it shows the single most important thing. Two colours are shared by both roles as
alerts; TX uses blue and RX green as its theme colour. Healthy searching and connected states use
the theme colour; alerts alternate it with their alert colour.

| Priority | State | Colour | Cadence | Notes |
| --- | --- | --- | --- | --- |
| 1 | Management mode | white | steady | outranks everything; appears after 0.5 s of session, so tool round-trips do not flash |
| 2 | Link loss | theme and red, equal halves | 2 Hz, 250 ms per colour | only after a first connection: either endpoint lost the DATA link |
| 3 | Data drops | theme and orange, equal halves | 2 Hz, 250 ms per colour | shown for one second after the drop counter moves |
| 4 | No root key | purple | 0.5 Hz, 200 ms on | time to run the management tool |
| 5 | Configured, not paired | theme and yellow, equal halves | 2 Hz, 250 ms per colour | waiting to be paired |
| 6 | Pairing | theme colour (blue TX, green RX) | 1 Hz, 300 ms on | |
| 7 | Searching | theme colour | steady | paired, no session yet; also indicates TX/RX role after boot |
| 8 | Connected | theme colour | fast: 4 Hz, 200 ms on; medium: 4 Hz, 50 ms on; slow: 2 Hz, 250 ms on | LQ >=80% fast, 50-79% medium, <50% slow; full brightness |
| - | MCUboot serial recovery / firmware update | white | 2 Hz, 250 ms on and 250 ms off | full brightness; driven by the bootloader while the application is stopped |

Trade-offs:

- **Production brightness is 100 %**: the production output uses the full palette. Debug builds
  use the minimum nonzero brightness, 1%.
- **Connected is never steady**: LQ selects cadence and duty, not brightness; fast and medium both
  run at 4 Hz, while low LQ uses a half-on 2 Hz pattern.
- **Link loss alternates theme and red**: it is suppressed until the first connection, so a device
  that never connected shows its normal state.
- **Link loss outranks every link state**: the first thing the user needs to know is that there
  is no usable link — and it is suppressed until the first connection, so a device that never
  connected shows its normal state instead of a false alarm.
- **Recent drops replace the link pattern temporarily**: theme/orange alternation makes a degraded
  data path visible without obscuring management or link loss status.

## Ownership and timing constraints

One low-priority UI thread owns button debounce, long-press detection and LED
output. Buttons are sampled every 20 ms, LED rendering runs at 20 Hz and updates
the device only when output changes. Waiting must respect the next input sample
and display edge.

Producers publish link, serial and management facts through zbus. UI alone decides
priority, colour and cadence. Channel locks must be released before hardware output.

Long presses are cumulative events, so delayed consumption or coalesced
notifications cannot lose a request. The application consumes them at frame
boundaries and starts pairing in the protocol's owning thread.

LED writes must not block the radio thread or feed its watchdog. Output failure
leaves the last physical colour and must be reported honestly. A board without a
LED or button alias omits that device's behavior.

Management white starts only after 500 ms; a recent-drop pattern lasts one second.
Production brightness is 100%, debug brightness is 1%, the minimum nonzero setting.
Recovery shows its own white 2 Hz indication while the application is stopped.

## Terminal output

All device operations use `python3 tools/zlrs.py COMMAND [options]`. `--help` lists management,
update and recovery commands; options follow the command. Status is grouped into
Device, Link and Configuration sections, with aligned labels and values. Device listings align
indices with management ports. Successful command and failure messages use explicit `[OK]` and
`[ERROR]` markers; leaving management mode successfully does not add extra ACK lines.

The updater starts with an aligned summary of the target, image path, file size and SHA256.
Each of its six stages has a numbered heading, with ports and verification hashes below it.
Upload progress is streamed live. The final result distinguishes a confirmed upgrade from an
upload that still needs verification or confirmation.

Headings and result markers use colour when the output is a terminal. Redirected output stays
plain, and `NO_COLOR` or `TERM=dumb` disables colour. Build strings and image-hash responses
remain plain values for use by scripts. `--help` includes examples and command purposes;
`<command> --help` describes parameters. `--dry-run` previews operations without opening ports.
