# User experience: the button and the status LED

The device has no screen, so all the user can touch is **one button** and **one RGB LED** (the
WS2812 on the RP2350-Zero). This document fixes what those two mean. Ports and modes:
[07-firmware](07-firmware.md); protocol: [08-protocol](08-protocol.md).

The goal: **you can tell what state the device is in without a computer**, and never by colour
alone — colour and cadence both carry information.

## Button

The button has exactly one action:

| Action | Condition | Result |
| --- | --- | --- |
| Long press | hold for 1 s or more (`CONFIG_ZLRS_APP_PAIR_HOLD_MS`) | start pairing (the handshake) |

There is no short press: releasing before 1 s does nothing. Pairing has consequences, so it is
worth holding a moment longer and cannot happen by accident. Re-binding is a long press too: the
new pairing record replaces the old one; there is no separate unpair action.

The button is standard equipment: the carrier board has one (SW1, GP12 to ground with an
internal pull-up); on the prototype a jumper wire from GP12 to GND stands in for it. A board
without the alias simply has no button and pairing comes from the management tool.

**Configuration does not use the button**: management mode is entered by a command the tool sends on
the management CDC (see [09-security](09-security.md) 9), with no physical action at all.

One press triggers pairing once; a new press needs a release in between. TX and RX share the
same button semantics.

## Status LED

One pixel cannot say much, so the LED uses both **colour and cadence** with fixed priorities: at
any moment it shows the single most important thing. Two colours are shared by both roles as
alerts; TX uses blue and RX green as its theme colour, so a healthy link only ever shows the
theme colour.

| Priority | State | Colour | Cadence | Notes |
| --- | --- | --- | --- | --- |
| 1 | Management mode | white (shared alert colour) | 1 Hz, 500 ms on | outranks everything; only after 0.5 s of session, so tool round-trips do not flash |
| 2 | Failsafe | red (shared alert colour) | 1 Hz, 800 ms on | only after a first connection: the TX hears no stick data, or the RX lost the link |
| 3 | No root key | purple (shared alert colour) | 0.5 Hz, 200 ms on | time to run the management tool |
| 4 | Configured, not paired | yellow (shared alert colour) | 1 Hz, 120 ms on | waiting to be paired |
| 5 | Pairing | theme colour (blue TX, green RX) | 1 Hz, 300 ms on | |
| 6 | Searching | theme colour | 0.5 Hz, 150 ms on | paired, no session yet |
| 7 | Connected | theme colour | fast: 100 ms/500 ms; medium: 200 ms/1 s; slow: 200 ms/2 s | LQ >=80% fast, 50-79% medium, <50% slow; brightness is always 30% |
| - | Boot self-test | theme colour | steady for 1.5 s | tells TX from RX at a glance |
| - | Data drops (overlay) | orange (shared alert colour) | one 300 ms flash every 2 s | only overlays while connected |

Trade-offs:

- **30 % brightness ceiling**: this is an indicator, not a lamp: it does not glare at night and
  costs nothing in the power budget.
- **Connected is never steady**: a short, fast heartbeat makes a long-running USB stall visible;
  lower LQ slows the heartbeat rather than dimming it, while pairing, searching and configuration
  use their own slower cadences so their states remain distinct.
- **Failsafe outranks every link state**: the first thing the user needs to know is that there
  is no usable link — and it is suppressed until the first connection, so a device that never
  connected shows its normal state instead of a false alarm.
- **The drop hint overlays rather than replacing**: the link still runs, it is just not clean.

## Where it lives

| Part | Location |
| --- | --- |
| State to colour and cadence | `core/led/led.c` (pure C, host-tested in `tests/host/test_led.c`) |
| System state broadcast | `app/src/state/sys_bus.h` (zbus channels `zlrs_link_chan`, `zlrs_alert_chan`, `zlrs_mode_chan`) |
| LED thread | `app/src/ui/led.c` (subscriber, 20 Hz render loop, decides the frame and writes the strip) |
| Button read and debounce | `app/src/ui/button.c` (its own thread, 20 ms sample; the hold goes on the bus) |

The button has its own thread, the same shape as the LED: it owns the GPIO and the debounce,
measures the hold, and reports *that a hold happened* on the system state bus
(`app/src/state/sys_bus.h`, a counter so a late reader still sees it). The link thread turns that
into a pairing request, which is what keeps the link state machine on one thread
([06-architecture](06-architecture.md) 6). A board without the alias simply has no button.

The LED does not live there any more, and it is no longer fed a colour. The producers publish
**facts** on zbus — what the control link is doing, which alerts are up, whether a management
session is open (`app/src/state/sys_bus.h`) — and the LED thread is the consumer that turns those
facts into what the table above describes. The question that table answers ("what wins when the
device is in management mode *and* the link is lost") is answered in one place, by the party that
renders it: the priority order and the colours are `core/led` (pure C, host-tested) and the LED
thread is their only caller. A producer knows nothing about colours, cadence or priorities.

The reason for the split is the last step of the path: a strip write costs a PIO push plus the
WS2812 latch delay, and the main loop is the superframe, so the one step that can block is no
longer on the radio's thread. The LED thread is preemptive, which means it only runs while the link
thread is blocked (see [06-architecture](06-architecture.md) 6), and the strip ends up with
exactly one writer. The thread renders at 20 Hz and pushes a frame only when the colour changed —
the strip holds what it was given, so repeating a frame costs a PIO push and buys nothing.

What happens after the colour is not this file's business either: the strip is written through
Zephyr's `led_strip` device API, so whatever the board puts behind the `zlrs-led` alias — a WS2812
on PIO, a strip on SPI or UART, an APA102 — works without a line of per-kind code. A board without
that alias simply has no device and the thread has nothing to show.

The cost is one thread (2 KB of stack) and three small channels, and one behaviour change worth
knowing: the LED is no longer part of the watchdog's path. A stuck main loop still resets the
board, but a stuck *strip* only freezes the last colour — the write path reports that once
(`led strip update failed ... status led is stale`) instead of pretending the state changed.

The thread also owns the timings the broadcast does not carry: white only shows once a management
session has lasted 500 ms (a tool round-trip must not flash), the drop overlay lasts a second after
the drop counter moves, and the boot self-test shows the role colour for its window unless an
alarm is already up — an alarm never waits for a boot indicator to finish.

## Terminal output

All device operations use `python3 tools/zlrs.py COMMAND [options]`. `--help` lists management,
update, recovery and throughput commands; options follow the command. Status is grouped into
Device, Link and Configuration sections, with aligned labels and values. Device listings align
indices with management ports. Successful command and failure messages use explicit `[OK]` and
`[ERROR]` markers; leaving management mode successfully does not add extra ACK lines.

The updater starts with an aligned summary of the target, image path, file size and SHA256.
Each of its six stages has a numbered heading, with ports and verification hashes below it.
Upload progress is streamed live. The final result distinguishes a confirmed upgrade from an
upload that still needs verification or confirmation.

Headings and result markers use colour when the output is a terminal. Redirected output stays
plain, and `NO_COLOR` or `TERM=dumb` disables colour. Build strings and image-hash responses
remain plain values for use by scripts. `--help` includes examples and command purposes;
`<command> --help` describes parameters. `--dry-run` previews operations without opening ports.
