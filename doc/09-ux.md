# User interface

ZLRS provides one pairing button and one RGB status LED. Color and cadence together
identify state. USB DATA, management and console behavior is specified in
[firmware](06-firmware.md).

## Button

Holding the button for at least one second starts pairing. A shorter press has
no action. Each hold fires once and requires release before another request.
Both roles use the same action. Pairing a new peer replaces the saved pairing.

The prototype uses GP12-to-ground wiring with an internal pull-up; the carrier
specifies a fitted button. Hardware without a button uses the management `pair`
command. Configuration and management entry are USB commands, independent of
button input.

The UI samples every 20 ms and publishes cumulative long-press counts. The
application consumes requests at frame boundaries; delayed or coalesced
notifications cannot erase a pending request.

## LED priority and cadence

Leader uses a blue theme and Follower a green theme. The highest applicable priority wins.

| Priority | Condition | Color | Cadence |
| --- | --- | --- | --- |
| 1 | Management session lasting at least 500 ms | White | Steady |
| 2 | Initialization fault, or loss/acquisition after a first connection | Theme / red | Alternate every 250 ms |
| 3 | Increased DATA drop counter | Theme / orange | Alternate every 250 ms, for 1 s |
| 4 | No root key | Purple | 200 ms on per 2 s |
| 5 | Configured, unpaired | Theme / yellow | Alternate every 250 ms |
| 6 | Pairing | Theme | 300 ms on per 1 s |
| 7 | Paired, searching for a session | Theme | Steady |
| 8 | Connected, high LQ | Theme | Flash on all three beats |
| 8 | Connected, medium LQ | Theme | Flash on the first two beats |
| 8 | Connected, low LQ | Theme | Flash on the first beat |

Connected indication uses the actual active band and running band mode. Each
cycle has three beats; SubG runs at half the 2.4 GHz cadence:

| Mode / active band | High LQ (three flashes) | Medium LQ (two flashes) | Low LQ (one flash) | Beat / cycle | On / off per occupied beat |
| --- | --- | --- | --- | --- | --- |
| Fixed 2.4 GHz | At least 80% | 50–79% | Below 50% | 300 / 900 ms | 150 / 150 ms |
| Fixed SubG | At least 80% | 50–79% | Below 50% | 600 / 1800 ms | 300 / 300 ms |
| Automatic / 2.4 GHz | At least 99% | 95–98% | Below 95% | 300 / 900 ms | 150 / 150 ms |
| Automatic / SubG | At least 80% | 50–79% | Below 50% | 600 / 1800 ms | 300 / 300 ms |

LQ is the local receive quality. In automatic mode, the 2.4 GHz boundaries align
with the existing LQ conditions for raising power (below 99%) and automatic
PHY downgrade (below 95%), making degradation visible before changing profile. Fixed mode
retains the original boundaries across the full LQ range because it never falls
back to another band. SubG retains those boundaries in both modes. These LED
bands do not change RF policy: profile changes also consider peer quality, RSSI and
qualification time. Healthy SubG feedback can schedule a return probe without
changing its connected LQ indication.

An empty beat is off throughout, with no additional gap between cycles. High
quality flashes evenly; medium quality has a 450 ms dark interval on 2.4 GHz or
900 ms on SubG after two flashes; low quality has a 750 ms dark interval on
2.4 GHz or 1500 ms on SubG after one flash. A band change selects the new cadence
and LQ boundaries on the next UI render, including when LQ is unchanged.

Link-loss indication is suppressed until the first connection; an initialization
fault does not require a preceding connection. Automatic capture after a
connection counts as link loss even if the logical session remains valid.
The higher-priority management, alarm, pairing and search indications retain
their cadences during a band change.

Production application output uses full palette brightness. Debug application
output defaults to the minimum nonzero brightness setting, 1%. Connected LQ
changes cadence rather than brightness. MCUboot recovery uses a separate white
2 Hz pattern, 250 ms on and 250 ms off, while the application is stopped.

## Output and observation contract

One low-priority UI thread owns input timing and LED output. Rendering follows
an absolute 50 ms frame grid (20 Hz), resolving each 150/300 ms connected pulse
without accumulating wakeup or notification drift. Status arrives through copied RF,
serial and management channels. Periodic reads recover missed notifications;
locks are released before GPIO or LED operations.

LED hardware is written only when color changes or a failed write needs retry.
Failure leaves the displayed output stale and is reported; it cannot be presented
as successful output. UI work cannot extend RF deadlines or feed the RF watchdog.
A board without a ready LED omits local indication while retaining status access.

## Host tool presentation

Device operations use `python3 tools/zlrs.py COMMAND [options]`. Command-specific
options follow the command. `--help` describes management, update and recovery;
`COMMAND --help` describes parameters. `--dry-run` previews the operation without
opening a device port.

Status groups device identity, link observations and configuration with aligned
labels. It distinguishes band mode, active band, acquisition and pending
transition. Local/peer quality, power, MCU temperature and an LR2021 section
include unavailable markers rather than fabricated zero measurements.

Device listings align serials with management ports. Result messages use `[OK]`
and `[ERROR]`. Successful automatic exit from management does not add redundant
ACK lines. Build and image-hash commands return plain values for scripts.

The updater presents the target, image path, size and SHA-256, then numbered
stages with live upload progress and verification hashes. Its result distinguishes
upload, verified boot and confirmed installation. Terminal output may use color;
redirected output is plain, and `NO_COLOR` or `TERM=dumb` disables color.
