# 安全模型：身份、配对与密钥

本文定义 zlrs 的安全模型：谁能连、怎么建立、密钥从哪来、挡得住什么。

设计约束：不做产线、不用全局公共密钥、用户自己配密钥、
多台设备共享根密钥但同一时刻只有已配对的两台能通。

## 1. 结论摘要

- 身份层分两级：**信任域**（根密钥，多台共享）与**配对**（决定当前是哪两台在通）。
- 根密钥不是链路凭据，而是**配对的授权凭据**。
- **同一时刻只保留一个配对**，换绑靠重新配对。
- **配置走有线**（每台设备一次，写入根密钥），**配对走空中**（按键触发）。
- 配对是按键触发的三次握手，只交换设备标识并互相认证，**空中不传任何密钥**。
- 设备身份由首次启动时的 RNG 自行生成，**不需要产线**。

## 2. 数据

| 名称 | 长度 | 来源 | 可见性 |
| --- | --- | --- | --- |
| `root_key` | 32 B | 用户配置（配置工具写入） | 保密 |
| `salt` | 16 B | 固定常量，含 KDF 版本号（如 `zlrs/kdf/v1`） | 公开 |
| `dev_id` | 4 B | 首次启动 RNG 生成，存 NVS | 可公开 |
| `pair_key` | 32 B | 配对时派生，不存储（可重算） | 保密 |

`dev_id` 是必需的：它既参与 `pair_key` 的派生，也是配对记录的内容。
它同时用于标识设备（配置工具与日志里显示「已绑定到 XXXX」），
也为多配对留出位置。

`dev_id` 在派生前按数值排序后拼接，保证两端算出同一个 `pair_key`。
它本身不是秘密——配对时会明文交换，冒充它需要先通过 MAC 认证。

未配置 `root_key`（全零）的设备不参与任何配对，也不接受数据。

## 3. 派生结构

```
root_key (32B, 用户配置, 组内共享)
  auth_key = KDF(root_key, "zlrs/auth")                  -> 配对握手认证

  配对后:
  pair_key = KDF(root_key, "zlrs/pair", dev_id_a, dev_id_b)   # 两端算出同一个
    fhss_seed = KDF(pair_key, "zlrs/fhss")[:4]           -> 跳频表种子
    sync_ctrl = KDF(pair_key, "zlrs/sync/control")[:4]   -> sub-GHz 同步字
    sync_data = KDF(pair_key, "zlrs/sync/data")[:4]      -> 2.4G 同步字
    link_auth = KDF(pair_key, "zlrs/link-auth")          -> 每包 tag
    link_enc  = KDF(pair_key, "zlrs/link-enc")           -> 可选加密
    session   = KDF(pair_key, "zlrs/session", nonce_t)   -> 每次会话重新生成
```

链路层只接触派生值，不直接接触 `root_key`。这样换 KDF、加前向保密、
改密钥长度都不影响协议本身。

`pair_key` 由双方 `dev_id` 确定性派生，因此不需要存储，也不需要握手来协商密钥——
握手只负责确认对方的 `dev_id`。会话密钥仍然每次连接用新 nonce 生成。

关键性质：**上空中出现的三个值（`fhss_seed` 与两个同步字）都是 `pair_key`
的单向派生值**，听到它们也推不出密钥。ELRS 是直接把 UID 发出去，
等于把凭据发出去。

## 4. 配对流程

前提：两端都已配置同一个 `root_key`，且两端都物理进入配对模式
（按键长按），配对期间使用最低发射功率。

1. TX 长按按键进入配对模式并降到最低功率；RX 同样长按进入配对模式。
2. TX 发 `PAIR_REQ`，携带 `dev_id_a`、`nonce_a` 与 `MAC_a`。
3. RX 校验 `MAC_a`，记下 `dev_id_a`，生成 `nonce_b`，回 `PAIR_RESP`，
   携带 `dev_id_b`、`nonce_b` 与 `MAC_b`。
4. TX 校验 `MAC_b`，记下 `dev_id_b`。双方各自派生 `pair_key` 及其派生值。
5. TX 发 `PAIR_CFM`（携带 `MAC_c`）；RX 校验后记下配对、退出配对模式。
6. TX 记下配对、退出配对模式，恢复功率，进入常态。

两端落盘的只有对方的 `dev_id` 与配对状态；`pair_key` 每次用时重新派生，不存储。

MAC 定义：

```
MAC_a = MAC(auth_key, "zlrs/pair/req"  || dev_id_a || nonce_a)
MAC_b = MAC(auth_key, "zlrs/pair/resp" || dev_id_b || nonce_a || nonce_b)
MAC_c = MAC(auth_key, "zlrs/pair/cfm"  || dev_id_b || nonce_b)
```

MAC 里同时包含两个 nonce，因此无法重放旧握手。

因为 `root_key` 两端都已经有（见第 10 节），配对过程**不传输任何密钥**，
只交换设备标识并互相认证。`pair_key` 由 `root_key` 与两个 `dev_id` 确定性派生，
两端各算一次，结果相同，不需要在空中协商。

### 规则

- 配对模式必须**物理按键**进入，且超时自动退出（建议 30 s）。
- 常态下设备**拒绝一切配对握手**，所以无法被远程抢占（换绑只能靠物理按键）。
- 配对成功即**替换**原有配对（同一时刻只保留一个）。
- 换绑靠一次新的配对握手：新记录顶掉旧记录，另一端在下一次配对或超时后失效。
- 同一时刻多台 RX 处于配对模式时先响应者胜出。所以配对时只给目标 RX 上电，
  或利用贴身低功率把覆盖范围压到最小。

## 5. 会话建立（与配对区分）

配对是一次性事件；**每次建立会话**是另一回事，而且不需要握手：

会话密钥由 TX 广播的随机数导出，本身不参与协商，所以单向广播就够——这不需要
用户参与，也不改任何持久状态，作用是不让重放与重启复用同一把流密钥。消息格式
与状态迁移见 [03-protocol.md](03-protocol.md) 第 3.5 节。

## 6. 对空中格式的影响

- **帧里不带任何身份字段**。过滤全部交给射频同步字：常态用
  `sync_ctrl` / `sync_data`，配对模式用槽 3 的公开常量。
  不匹配的包在射频层就被丢弃，MCU 不会被唤醒。
- 跳频表由 `fhss_seed` 生成，两端各自算，不需要在空中同步种子本身。
- 每包带序列号，用于防重放。
- 每包带 4 B tag（是否携带由 profile 决定，不由标志位决定）。
- 配对握手使用独立的包类型，只在配对模式下接收。

## 7. 安全性质与已知弱点

### 7.1 对手模型

| 级别 | 对手 | 能力 |
| --- | --- | --- |
| L1 | 同场飞友 | 误占频段；基本不可能知道你的短语 |
| L2 | 有 SDR 的爱好者 | 录包、重放、伪造、逆向固件 |
| L3 | 有组织的攻击者 | 长期监听、侧信道、社工 |

**本设计针对 L1 与 L2，明确不防 L3。** 由此产生的取舍：

- 不做前向保密（要做得在会话建立时加临时 ECDH）
- 接受"知道 `root_key` 的人能在配对窗口抢走配对"

对 L1/L2 而言，伪造一个包需要先破 HMAC-SHA256，这在现实中不可行。

### 7.2 分层

两个独立的威胁，分层解决：

| 威胁 | 谁 | 靠什么挡 |
| --- | --- | --- |
| 组内其它设备误占链路 | 有 `root_key` 的自己人 | 配对记录 + 逐对密钥 |
| 外部攻击者伪造/占用 | 没有 `root_key` | 每包 tag、会话 nonce |

注意第一类是**用密码学挡不住的**——组内设备本来就持有 `root_key`，
能算出任何一对的 `pair_key`。真正拦住它的是"只认配对时记下的 `dev_id`"
这条本地规则。所以配对的作用是**限制合法设备之间的互扰**，不是对抗攻击者。

**能防：**

- 不同用户之间的碰撞与误占（跳频种子与同步字都由密钥派生，看起来像随机数）
- 未配对设备占用链路，即使它知道 `root_key`
- 报文伪造（每包 tag）与重放（序列号加会话 nonce）
- 配对过程的中间人（三次握手都带 MAC，不是 Just Works）

**防不住：**

- **`root_key` 泄露**。拿到根密钥的人可以主动与任何同组设备配对，把你原来的
  配对顶掉。缓解手段是配对需要物理接触加按键，攻击者得在你按下按键的窗口内靠近。
- **没有前向保密**。根密钥泄露后，过去录下的加密流量可被解开。要解决需要在
  连接握手里加临时 ECDH；本设计接受这个代价。
- **同一根密钥的成员之间可以互相冒充**。这是没有逐设备身份的固有代价。
- **撤销只能逐台做**。丢设备时要在另一端重新配对一次（新记录顶掉旧的），
  而不是吊销密钥。

## 8. 参数与算法

- 用户输入形式：**短语**。
- 加密：**默认关闭**，理由见下，按 profile 打开（见
  [03-protocol.md](03-protocol.md) 2.3）。
- MAC 算法：**HMAC-SHA256 截断到 4 B**。这样 PBKDF2 / HKDF / MAC 全落在
  SHA-256 一族，P1 profile 不必引入 AES；只有 P2（加密）才需要 AES-CTR。
- KDF：**放在设备侧**，理由见下。
- RX 的密钥来源：**有线配置**（见第 10 节）。
- salt：**固定常量**，含版本号，不保密。
- 短语最小长度：**12 字符**；低于 16 字符给出强度提示，配置工具支持一键生成。

### 加密默认关闭

因为**机密性可以下放，认证不能**。这两件事必须分开看：

| | 能否下放到应用层 | 原因 |
| --- | --- | --- |
| **机密性**（加密） | 能 | 应用层若已端到端加密，链路层再加密是重复开销 |
| **完整性 / 来源** | **不能** | 见下 |

认证不能下放，有三个理由：

1. **控制链路没有"应用层"可以托管。** RC 帧是 TX 固件自己产生的，不是从串口
   来的。链路层不认证，就等于谁能往空中发 RC 帧谁就能控制飞机。
2. **同步字是过滤器，不是凭据。** 它空中明文传输，攻击者收一包就学到了，
   然后就能用这个同步字伪造包。
3. **应用层加密挡不住注入。** 解密出来发现是垃圾时，包已经进了接收窗口。

所以：**tag 必须有，加密可以默认关。** 这就是 P1 profile。

链路加密保留为可选档，给"透传载荷本身没有加密"的场景用——裸 MAVLink、
原始串口数据。配置工具应该让用户明确选择，而不是让他以为链路默认就是安全的。

### PBKDF2 迭代次数

迭代次数取 100,000，对应在目标 MCU 上约 1–2 秒的耗时。

**迭代次数随 KDF 版本号发布，发布后不能原地修改。** 改了之后同一个短语会
派生出不同的 `root_key`，新旧固件的设备就通不了了。所以：

- `salt` 里必须含 KDF 版本号（`zlrs/kdf/v1`）
- 将来要调整迭代次数，是**发一个新版本**，而不是原地改数
- 配置工具要允许选择版本，这样新旧设备能用同一版本互相配置

不这么做的后果是：某次固件升级之后，所有设备必须重新配置、重新配对，
而用户不会知道为什么。

### salt 固定

盐的作用是防止预计算。但要满足"同一个短语在两台设备上导出同一个密钥"，
两端必须使用**同一个**盐——所以盐不能是每台设备随机生成的。

配置工具理论上可以在写入密钥时生成一个随机盐、同时写进两台设备，但代价是：
以后想再加一台设备时，必须同时知道那个盐。丢了盐就只能全部重配、所有配对作废。
而且对弱短语来说，随机盐并不能救场——攻击者针对单台设备暴力枚举字典的成本，
和针对固定盐预计算一次的成本，在弱口令面前是同一个量级。

所以采用**固定的、随协议版本走的公开盐**，把防护放在迭代次数和短语长度上。
盐在这里的价值是卫生性的：让 zlrs 的哈希空间与其它应用区分开。

### 算法选型

| 用途 | 算法 | 备注 |
| --- | --- | --- |
| 短语 → 根密钥 | PBKDF2-HMAC-SHA256 | 固定 salt + 高迭代 |
| 根密钥 → 派生值 | HKDF-SHA256 | info = 标签，需要时再接上下文 |
| 每包 tag | HMAC-SHA256 截断 4 B | 覆盖 header + seq + payload |
| 可选加密（P2） | AES-CTR | MAC 覆盖密文（encrypt-then-MAC） |

算法实现是仓库自带的一份纯 C 原语（`lib/proto/crypto_soft.c`）。选它而不是
mbedTLS/PSA 的理由是设备与主机共用同一份源码，主机侧测试不需要 Zephyr 工作区；
代价是没有硬件加速、也没有经过第三方审计，属于"自己担着"的部分。
接口是一层薄封装（`include/zlrs/proto/crypto.h`），要接 PSA Crypto 或硬件加速时
只替换那一个实现文件。

短语到密钥必须走 KDF，不能用裸哈希。

固定 salt 意味着所有 zlrs 用户共享同一张预计算表的暴露面，这是「同一短语在两端
导出同一密钥」的必然代价，用高迭代次数与短语长度补偿。

### KDF 放在设备侧

理由：

1. **派生规则唯一**。任何配置器（官方、第三方、网页版）送同一个短语进设备，
   必须得到同一个密钥。若各家工具各自实现 KDF，就会互不兼容，生态直接分裂。
   ELRS 正是靠"推导在固件里"才有这个性质。
2. **参数不被工具削弱**。迭代次数、salt、标签由固件定义，第三方工具改不了。

代价是设备要跑 PBKDF2。但这只在**配置那一刻**发生一次，不是每次启动，
所以可以接受高迭代次数。前提是设备只存派生后的密钥，不存短语。

## 9. 分层边界

协议核心不接触短语，也不接触 `root_key`，只接收已经派生好的
`fhss_seed`、两个同步字与 `link_auth` / `link_enc`。

## 10. RX 如何取得根密钥

第 4 节的配对流程假设**两端都已经有同一个 `root_key`**。二者是分开解决的两个问题：

| 事件 | 何时发生 | 怎么传 |
| --- | --- | --- |
| **配置**（写入 `root_key`） | 每台设备一次 | 有线，见下 |
| **配对**（记录 `dev_id`） | 需要换绑时 | 空中，按键触发 |

### 配置方式：有线写入

新 RX 接一次串口，由配置工具写入 `root_key`（以及首次生成的 `dev_id`）。

好处：

- 之后所有配对都是**有认证的**，不存在"首次信任"窗口。
- 安全模型简单，不需要解释 TOFU。
- 对 DIY 场景而言，用户本来就要焊板子、刷固件，接一次串口配密钥是自然的步骤。

代价：

- 每台新 RX 都要接一次线。**换绑不需要**——配对走空中按键，所以装进机身之后
  仍然可以重新配对。
- 与 ELRS 的"上电即可绑定"相比，首次使用多一道工序。这个取舍需要在用户手册里
  写清楚。

### 配置通道

**配置协议跑在数据通路上**：数据 UART，以及 USB 的数据 CDC。TX 与 RX 完全一样。

用同一条通路的代价是它要和透传数据争用，解法是**按键的时机**：

| 时机 | 行为 |
| --- | --- |
| **开机时按住按键** | 进入配置模式 |
| **开机后按按键** | 配对 |

正常运行时数据通路是透传口；进入配置模式后透传暂停，改跑配置协议。
两种用途不会同时争用，而且"进入配置模式"是个**不可远程触发的物理动作**，
这一点对安全有实际好处。

### 配置协议的帧与命令

帧形状（见 `include/zlrs/config/config.h`）：

```
[0xA5][0x5A][ver=1][cmd][len][payload][crc8]      crc 覆盖 ver..payload
```

命令分两侧：主机发的是状态查询、触发配对、写根密钥（64 个十六进制字符）、
写短语、写失控值（22 字节 CRSF 通道载荷）、改数据口波特率、退出；设备回
`ACK`（带上原命令与状态码）或 `STATUS`（16 字节：角色、链路状态、标志、
`dev_id`、`peer_id`、LQ）。参数不合法、落盘失败、命令不认识都如实回状态码。

两条与安全相关的规则：

- **短语的派生规则固定在设备侧**（salt 与迭代次数都由固件定），配置工具只送
  短语。这样第三方工具没法用弱参数派生，新旧固件的派生结果也一致。
- **配置模式只能靠按键进入**，没有远程入口；运行时数据口只是透传口。

仓库里带一个最小的命令行工具 `scripts/zlrs-config.py`（读状态、触发配对、
写密钥/短语、写失控值、改波特率、退出；`--self-test` 校验组帧与固件一致）。
它只是把上面这套帧包装了一层，任何第三方工具按同样的帧格式说话都能用。

不设专门的控制口是有意的——TX 和 RX 用完全相同的流程，用户只需要记一套操作。
代价是 TX 也不能在运行时边透传边配置。

配置模式在超时（建议 5 分钟）或收到明确的退出指令后结束，避免用户配完忘了、
结果透传一直不通。
