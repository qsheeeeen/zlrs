# Security model

Who may connect, how a link is established, where the keys come from and what this stops. Frame formats: [09-protocol](09-protocol.md); firmware behaviour: [08-firmware](08-firmware.md).

Constraints: no production line, no global shared key, the user brings their own key, several devices may share a root key while only one paired pair can talk at a time.

## 1. Summary

- Identity has two levels: the **trust domain** (a shared root key) and the **pairing** (which two devices are speaking right now).
- The root key is not a link credential but the **authority to pair**.
- One pairing exists at a time; rebinding is another pairing.
- **Configuration is wired** (the config CDC, once per device, to write the root key); **pairing is over the air** (a long press).
- Pairing is a three-way handshake: it exchanges device ids and two random numbers with mutual authentication and never puts a key on air.
- Device identity is generated by the RNG on first boot, so no production line is needed.

## 2. Data

| Name | Length | Source | Visibility |
| --- | --- | --- | --- |
| `root_key` | 32 B | user configuration (written by the config tool) | secret |
| `salt` | 16 B | a fixed constant carrying the KDF version (`zlrs/kdf/v1`) | public |
| `dev_id` | 4 B | RNG on first boot | public |
| `pair_salt` | 8 B | one nonce from each end during pairing | public |
| `pair_key` | 32 B | derived while pairing, never stored (recomputed from `dev_id` and `pair_salt`) | secret |

`dev_id` and `pair_salt` sit in NVS and travel in the clear while pairing; neither is a secret, and impersonating a `dev_id` still has to pass the MAC. A device with no `root_key` neither pairs nor accepts data.

## 3. Derivation tree

```
root_key (32B, user configured, shared inside the group)
  auth_key = KDF(root_key, "zlrs/auth")                  -> pairing handshake authentication
  pair_key = KDF(root_key, "zlrs/pair", sort(dev_id_a, dev_id_b) || sort(nonce_a, nonce_b))
    fhss_seed = KDF(pair_key, "zlrs/fhss")[:4]           -> hop table seed
    sync_ctrl = KDF(pair_key, "zlrs/sync/control")[:4]   -> sub-GHz sync word
    sync_data = KDF(pair_key, "zlrs/sync/data")[:4]      -> 2.4G sync word
    link_auth_ab = KDF(pair_key, "zlrs/link-auth", dev_id_a || dev_id_b)  -> per-frame tag
    link_auth_ba = KDF(pair_key, "zlrs/link-auth", dev_id_b || dev_id_a)  -> the other direction
    session_ab   = KDF(pair_key, "zlrs/session", nonce_t || nonce_r || dev_id_a || dev_id_b)
    session_ba   = KDF(pair_key, "zlrs/session", nonce_t || nonce_r || dev_id_b || dev_id_a)
                                                          -> a fresh pair per session
    link_enc  = KDF(pair_key, "zlrs/link-enc")            -> P2 encryption key (last)
```

The link layer only touches derived values, never `root_key`. The `pair_key` context is the two `dev_id`s **in sorted order** plus the two pairing nonces **in sorted order**: sorting lets each end derive once and agree, and the nonces separate "this pair of devices" from "this pairing", so every pairing changes `pair_salt` and retires old recordings. The price is that `pair_salt` has to be stored.

`link_auth` and `session` are each a pair of keys whose direction comes from the order of the two `dev_id`s: outgoing frames use out, verifying the peer uses in. One key for both directions would let our own frame, echoed back, pass as the peer's (reflection).

The three values that appear on air (`fhss_seed` and the two sync words) are one-way derivations of `pair_key`, so hearing them yields no key.

## 4. Pairing flow

Preconditions: both ends carry the same `root_key`, both physically enter pairing mode (a long press) and pairing runs at the lowest TX power.

1. The TX enters pairing mode on a long press and drops to minimum power; the RX does the same.
2. The TX sends `PAIR_REQ` carrying `dev_id_a`, `nonce_a` and `MAC_a`.
3. The RX verifies `MAC_a`, remembers `dev_id_a`, draws `nonce_b` and answers `PAIR_RESP` with `dev_id_b`, `nonce_b` and `MAC_b`.
4. The TX verifies `MAC_b` and remembers `dev_id_b`; both ends derive `pair_key` and the tree below it.
5. The TX sends `PAIR_CFM` with `MAC_c`; once it verifies, the RX stores the pairing and leaves pairing mode.
6. The TX stores the pairing, leaves pairing mode, restores power and goes back to normal.

```
MAC_a = MAC(auth_key, "zlrs/pair/req"  || dev_id_a || nonce_a)
MAC_b = MAC(auth_key, "zlrs/pair/resp" || dev_id_b || nonce_a || nonce_b)
MAC_c = MAC(auth_key, "zlrs/pair/cfm"  || dev_id_b || nonce_b)
```

The MACs cover both nonces, so an old handshake cannot be replayed; the three messages carry their own labels and the state machine holds the roles. Pairing **transfers no key**: it authenticates `dev_id`s and exchanges two nonces.

Rules:

- Pairing mode needs a **long press** and times out after 30 s.
- In normal operation a device refuses every pairing handshake, so it cannot be taken over remotely.
- A successful pairing **replaces** the previous one (only one exists at a time); rebinding is simply a new pairing.
- With several RXs in pairing mode the first responder wins, so power only the intended RX or use low power at close range to shrink the coverage.

## 5. Session setup (distinct from pairing)

Pairing decides who we talk to; the session decides which key this conversation uses. `pair_key` is derived during pairing, and a session only feeds it two fresh nonces; no persistent state changes and the user is not involved. The flow is in [09-protocol](09-protocol.md) 3.5 and the security properties are:

- **One nonce from each end**: the TX offers `nonce_t`, the RX adds `nonce_r`, and both feed the session key. A TX-only value can be replayed whole: record an old `SYNC`, replay it, and the RX would recompute that session's key.
- **A session is adopted only after confirmation**: the TX tags a `SESS_CFM` with the new key and the RX adopts it only once that verifies; a replayed frame carries the old `nonce_r` and fails.
- **Only the traffic keys change, not the identity**: recomputing a session leaves the pairing record alone, and `nonce_t`, `nonce_r`, the session keys and sequence numbers are never stored, so power loss ends them.
- **`SYNC` is authenticated with the pairing-level `link_auth`**: the nonce is public, but nobody else can forge a session message that verifies.

## 6. What it means for the air format

- Frames carry no identity field: filtering is the radio's sync word, and non-matching packets are dropped at the radio layer.
- The hop table comes from `fhss_seed`, computed independently on each end.
- Every frame carries a sequence number (replay protection) and a 4 B tag (P0 has none; see [09-protocol](09-protocol.md) 2.3). Direction is not in the frame, it is in the tag key.
- Pairing uses dedicated packet types that are only accepted in pairing mode.

## 7. Security properties and known weaknesses

### 7.1 Adversary model

| Level | Adversary | Capability |
| --- | --- | --- |
| L1 | another pilot at the field | occupies the band by accident; cannot realistically know your passphrase |
| L2 | a hobbyist with an SDR | records, replays, forges and reverses firmware |
| L3 | an organised attacker | long-term monitoring, side channels, social engineering |

**This design targets L1 and L2 and explicitly not L3**: there is no forward secrecy (which would need ephemeral ECDH during session setup) and we accept that anyone who knows `root_key` can steal a pairing inside the pairing window. For L1 and L2, forging a frame means breaking HMAC-SHA256, which is not a practical option.

### 7.2 Layers

| Threat | Who | Held off by |
| --- | --- | --- |
| another device in the group grabbing the link | someone inside who has `root_key` | the pairing record plus per-pair keys |
| an outsider forging or occupying | no `root_key` | per-frame tags and session nonces |

The first kind **cannot be stopped with cryptography**: a device inside the group already holds `root_key` and `pair_salt` travels in the clear. What stops everyday interference is the local rule "only the `dev_id` from pairing is accepted": pairing limits interference **between legitimate devices**, it is not a defence against attackers.

What it stops: collisions and accidental occupation between different users, an unpaired device taking the link (even one that knows `root_key`), frame forgery and replay, reflection, old recordings after a rebind, and man-in-the-middle during pairing.

What it does not stop:

- **A leaked `root_key`**: whoever holds it can pair with any device in the group and displace the existing pairing. The mitigation is that pairing needs physical access and a button press.
- **No forward secrecy**: once the root key leaks, past recorded encrypted traffic can be read.
- **Group members can impersonate each other, and rebinding does not revoke a peer that heard the new pairing**: real revocation means changing `root_key`.
- **Revocation is per device.**
- **P0 has no authentication at all**: the maximum-performance profile carries no tag and can be injected into; trusted environments only (a racing course).

## 8. Parameters and algorithms

- User input is a **passphrase**, at least 12 characters, with a strength hint below 16; the config tool can generate one.
- MAC: HMAC-SHA256 truncated to 4 B, keeping PBKDF2, HKDF and the MAC inside the SHA-256 family so P1 needs no AES.
- The KDF lives on the **device** side: any configurator submitting the same passphrase gets the same key, and the parameters (rounds, salt, labels) are fixed by the firmware, out of reach of third-party tools.
- 100,000 rounds (about 1-2 s on the target MCU), published with the KDF version and never changed in place afterwards.
- The salt is fixed (it carries the version): the same passphrase has to derive the same key on two devices, so the salt cannot be per-device random; the protection sits in the rounds and the passphrase length.

Algorithm choices:

| Purpose | Algorithm |
| --- | --- |
| passphrase to root key | PBKDF2-HMAC-SHA256 |
| root key to derived values | HKDF-SHA256 |
| per-frame tag | HMAC-SHA256 truncated to 4 B |
| P2 encryption (last) | AES-CTR with the MAC over the ciphertext (encrypt-then-MAC) |

On target the primitives go through Zephyr's PSA Crypto (`core/proto/crypto_psa.c`); the host tests use a pure C implementation behind the same interface (`tests/host/crypto_soft.c`), and the two are checked against each other with fixed vectors.

## 9. Layering boundary

The protocol core never touches the passphrase or `root_key`: it receives `fhss_seed`, the two sync words, the directional `link_auth` and `link_enc`, and the inputs they derive from (both `dev_id`s and `pair_salt`). Session keys are computed inside the link layer from `nonce_t` and `nonce_r`.

## 10. Configuration channel

Configuration uses the **dedicated config CDC** (see [08-firmware](08-firmware.md) 1): plug in USB and configure, with **no extra authentication** — physical access to the USB port is the authorisation.

The tool first sends the enter-config-mode command on the config CDC; the radio then stops entirely, bytes arriving on the data port are dropped and counted, and everything resumes on exit (see [08-firmware](08-firmware.md) 2).

### The config protocol

```
[0xA5][0x5A][ver=2][cmd][len][payload][crc8]      crc covers ver..payload
```

Command set (covering every user parameter, see [08-firmware](08-firmware.md) 3):

| Command | Notes |
| --- | --- |
| read status | role, link state, flags, `dev_id`, `peer_id`, LQ, local sub-G hardware, region, power ceiling, data port baud rate |
| enter config mode | the formal entry |
| start pairing | enters the pairing window at once |
| erase pairing | effective on the next boot |
| write passphrase | the device derives the root key with PBKDF2 |
| write root key | 64 hex characters |
| write failsafe values | a 22-byte CRSF channel payload |
| set data port baud rate | effective on the next boot |
| set region | validated against the board's radio design on write, refused on mismatch; effective on the next boot |
| set power ceiling | never above the chosen region's limit; effective on the next boot |
| factory reset | wipes NVS, effective on the next boot |
| enter recovery | sets the boot-mode flag and reboots into MCUboot serial recovery |
| read build string | checks which version is running after an upgrade |
| read image hash | the update tool's verdict: the image just sent, or an older one after a rollback |
| confirm upgrade | the host confirms this upgrade; without it the image rolls back (see [08-firmware](08-firmware.md) 6) |
| exit | leaves config mode |

Every command gets an `ACK` (the command plus a status code) or a `STATUS`; bad parameters, failed writes and unknown commands all report their own status. Two security-related rules: **the passphrase derivation is fixed on the device**, and **config mode can only be entered from the config CDC** (debug builds also allow the shell on the console, see [12-debug](12-debug.md)).

The repository ships a minimal command-line tool, `tools/zlrs-config.py` (`--self-test` checks its framing against the firmware); any third-party tool that speaks the same framing works.
