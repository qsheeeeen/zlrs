# User experience: the button and the status LED

The device has no screen, so all the user can touch is **one button** and **one RGB LED** (the
WS2812 on the RP2350-Zero). This document fixes what those two mean. Ports and modes:
[08-firmware](08-firmware.md); protocol: [09-protocol](09-protocol.md).

The goal: **you can tell what state the device is in without a computer**, and never by colour
alone — colour and cadence both carry information.

## Button

The button has exactly one action:

| Action | Condition | Result |
| --- | --- | --- |
| Long press | hold for 1 s or more (`CONFIG_ZLRS_APP_PAIR_HOLD_MS`) | start pairing (the handshake) |

There is no short press: releasing before 1 s does nothing. Pairing has consequences, so it is
worth holding a moment longer and cannot happen by accident. Re-binding is a long press too: the
new pairing record replaces the old one; there is no separate unpair action.

The button is standard equipment: the carrier board has one (SW1, GP12 to ground with an
internal pull-up); on the prototype a jumper wire from GP12 to GND stands in for it. A board
without the alias simply has no button and pairing comes from the config tool.

**Configuration does not use the button**: config mode is entered by a command the tool sends on
the config CDC (see [10-security](10-security.md) 9), with no physical action at all.

One press triggers pairing once; a new press needs a release in between. TX and RX share the
same button semantics.

## Status LED

One pixel cannot say much, so the LED uses both **colour and cadence** with fixed priorities: at
any moment it shows the single most important thing. Two colours are shared by both roles as
alerts; TX uses blue and RX green as its theme colour, so a healthy link only ever shows the
theme colour.

| Priority | State | Colour | Cadence | Notes |
| --- | --- | --- | --- | --- |
| 1 | Config mode | white (shared alert colour) | 1 Hz, 500 ms on | outranks everything; only after 0.5 s of session, so tool round-trips do not flash |
| 2 | Failsafe | red (shared alert colour) | 1 Hz, 800 ms on | only after a first connection: the TX hears no stick data, or the RX lost the link |
| 3 | No root key | purple (shared alert colour) | 0.5 Hz, 200 ms on | time to run the config tool |
| 4 | Configured, not paired | yellow (shared alert colour) | 1 Hz, 120 ms on | waiting to be paired |
| 5 | Pairing | theme colour (blue TX, green RX) | 1 Hz, 300 ms on | |
| 6 | Searching | theme colour | 0.5 Hz, 150 ms on | paired, no session yet |
| 7 | Connected | theme colour | steady | LQ 80 or more is 30 % brightness, 50-79 is 18 %, below 50 is 10 % |
| - | Boot self-test | theme colour | steady for 1.5 s | tells TX from RX at a glance |
| - | Data drops (overlay) | orange (shared alert colour) | one 300 ms flash every 2 s | only overlays while connected |

Trade-offs:

- **30 % brightness ceiling**: this is an indicator, not a lamp: it does not glare at night and
  costs nothing in the power budget.
- **No fast blinking for steady states**: connected is steady; blinking is kept for states that
  are changing (pairing, searching) or need the user (config, unpaired, unconfigured).
- **Failsafe outranks every link state**: the first thing the user needs to know is that there
  is no usable link — and it is suppressed until the first connection, so a device that never
  connected shows its normal state instead of a false alarm.
- **The drop hint overlays rather than replacing**: the link still runs, it is just not clean.

## Where it lives

| Part | Location |
| --- | --- |
| State to colour and cadence | `core/led/led.c` (pure C, host-tested in `tests/host/test_led.c`) |
| System state broadcast | `app/src/sys_bus.h` (zbus channels `zlrs_link_chan`, `zlrs_alert_chan`, `zlrs_mode_chan`) |
| LED thread | `app/src/led_thread.c` (subscriber, 20 Hz render loop, decides the frame and pushes it) |
| WS2812 port | `app/src/led_port.c` (takes one abstract RGB frame → the strip: PIO plus the `led_strip` API, board node `zlrs-led`) |
| Button read and debounce | `app/src/main.c` (polled in the main loop, no extra thread) |

The button stays in the main loop: it is a millisecond-level level check, so a thread would buy
nothing, and a press has to be seen as an edge.

The LED does not live there any more, and it is no longer fed a colour. The producers publish
**facts** on zbus — what the control link is doing, which alerts are up, whether a config session
is open (`app/src/sys_bus.h`) — and the LED thread is the consumer that turns those facts into
what the table above describes. The question that table answers ("what wins when the device is in
config mode *and* the link is lost") is answered in one place, by the party that renders it: the
priority order and the colours are `core/led` (pure C, host-tested) and the LED thread is their
only caller. A producer knows nothing about colours, cadence or priorities.

The reason for the split is the last step of the path: a strip write costs a PIO push plus the
WS2812 latch delay, and the main loop is the superframe, so the one step that can block is no
longer on the radio's thread. The LED thread is preemptive, which means it only runs while the link
thread is blocked (see [07-architecture](07-architecture.md) 6), and the strip ends up with
exactly one writer. The thread renders at 20 Hz and pushes a frame only when the colour changed —
the strip holds what it was given, so repeating a frame costs a PIO push and buys nothing.

The two halves keep their distance: the thread knows what a state means and produces one
device-independent colour, the port knows how to put a colour on *this* device (colour order,
pixel count, reset timing — all devicetree). Neither can drift into the other's job: the port
takes an RGB triple and nothing else.

The cost is one thread (2 KB of stack) and three small channels, and one behaviour change worth
knowing: the LED is no longer part of the watchdog's path. A stuck main loop still resets the
board, but a stuck *strip* only freezes the last colour — the write path reports that once
(`led strip update failed ... status led is stale`) instead of pretending the state changed.

The thread also owns the timings the broadcast does not carry: white only shows once a config
session has lasted 500 ms (a tool round-trip must not flash), the drop overlay lasts a second after
the drop counter moves, and the boot self-test shows the role colour for its window unless an
alarm is already up — an alarm never waits for a boot indicator to finish.
