# 空中协议

本文定义 zlrs 的空中协议：物理层交给我们什么、帧长什么样、链路状态机怎么走、会话怎么建、超帧怎么排、速率与功率怎么自适应、跳频与法规怎么落地。身份与密钥见 [05-security](05-security.md)，线程与射频栈见 [03-architecture](03-architecture.md) 第 7 节，芯片数据见 [06-radio](06-radio.md)。

## 1. 物理层已经给了什么

设计帧之前先明确哪些不用自己做——LR2021 通过 RAC 已经提供：

| 能力 | 硬件提供 | 我们要做的 |
| --- | --- | --- |
| 前导码 | 是（`agc_pbl_len`） | 取值见 5.3 |
| 同步字 | 是（FLRC，3 个槽，每个 2 或 4 字节） | 用它做第一级过滤，见 1.1 |
| CRC | 是（`SetFlrcPacketParams`） | **不需要自己加 CRC** |
| 长度字段 | 是（变长包格式） | 不需要自己带长度 |

结论：**帧里不要重复携带 CRC 和长度**，这两样是射频链路层的活。

### 1.1 配对过滤用同步字

**帧里不放 `pair_id`，过滤交给射频同步字。**

同步字是硬件匹配的：不匹配的包在射频层就被丢弃，MCU 根本不会被唤醒。

| 槽 | 值 | 用途 |
| --- | --- | --- |
| 1 | `KDF(pair_key, "zlrs/sync/control")[:4]` | sub-GHz 控制链路 |
| 2 | `KDF(pair_key, "zlrs/sync/data")[:4]` | 2.4G 数据链路 |
| 3 | 公开常量 | 配对模式 |

这带来一个很强的性质：**配对之后，本机在物理层就听不到其它配对的流量**，不消耗任何 MCU 时间或空口字节。

同步字固定用 4 字节（32 位），这样才装得下派生值。速率档不编码进同步字——两端本来就必须处在同一速率才能通信。

代价：切换频段时要连同步字一起重配（本来就要改频率，顺带做掉）；配对改变后要重算一次。

## 2. 帧格式

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `header` | 1 B | 高 6 位 = 类型（64 种），低 2 位 = 标志 |
| `seq` | 2 B | 会话内递增，防重放、用于分片重组 |
| `payload` | 0..N B | 类型相关 |
| `tag` | 0 或 4 B | HMAC 截断，覆盖 header + seq + payload |
| `crc` | 硬件追加 | 由射频链路层生成与校验 |

`tag` 是否存在、载荷是否加密，由 **profile 决定，不由标志位决定**。否则攻击者只要清掉标志位就能把认证降级掉。

### 2.1 header 标志位

| 位 | 名称 | 含义 |
| --- | --- | --- |
| 0 | `MORE` | 分片未结束 |
| 1 | `ACK_REQ` | 请求对端确认 |

### 2.2 包类型

6 位类型空间共 64 种，当前占用 11 种。

| 值 | 类型 | 方向 | 说明 |
| --- | --- | --- | --- |
| 0 | `RC` | TX 到 RX | 遥控通道 |
| 1 | `TLM` | RX 到 TX | 遥测 |
| 2 | `DATA_UP` | TX 到 RX | 透传数据 |
| 3 | `DATA_DOWN` | RX 到 TX | 透传数据 |
| 4 | `ACK` | 双向 | 透传确认（ARQ profile 用） |
| 5 | `BEACON` | TX 到 RX | 会话建立、信道/跳频同步、profile 声明 |
| 6 | `PAIR_REQ` | TX 到 RX | 配对 |
| 7 | `PAIR_RESP` | RX 到 TX | 配对 |
| 8 | `PAIR_CFM` | TX 到 RX | 配对 |
| 9 | `SESS_RESP` | RX 到 TX | 会话响应，带 `nonce_r` |
| 10 | `SESS_CFM` | TX 到 RX | 会话确认，用新会话钥匙打 tag |
| 11–63 | 保留 | — | — |

### 2.3 安全 profile

| profile | tag | 加密 | 用途 |
| --- | --- | --- | --- |
| `P0` | 无 | 无 | 仅调试，不可用于实际飞行 |
| `P1` | 4 B | 无 | **默认** |
| `P2` | 4 B | AES-CTR | 认证加密；MAC 覆盖密文（encrypt-then-MAC） |

- `tag` = **HMAC-SHA256 截断到 4 B**，覆盖 `header` + `seq` + `payload`；钥匙按方向派生，见 [05-security](05-security.md) 第 3 节。
- 选 HMAC-SHA256 是为了让身份层**只用 SHA-256 一个原语**：PBKDF2、HKDF、MAC 全部落在同一族函数上，不必为 P1 引入 AES。P2 才需要 AES。
- `P2` 还没实现：链路层看到 P2 直接不发包，现在只有 P0（调试）与 P1 可用。
- profile 目前是**编译期配置**：`BEACON` 里声明的 profile 必须与本机一致，不一致直接丢弃。要让 RX 跟随 TX 就得按 profile 重配射频，那是另一件事（速率、tag 与加密路径都跟着变）。

### 2.4 控制帧载荷与速率档

| 项 | 默认 | 其它档位 |
| --- | --- | --- |
| 控制帧率 | **150 Hz** | 500 Hz（近距竞速档；实际生效值还会被地区占空比与空中时间压档，见 4.1） |
| 通道数 | 16 | — |
| 每通道位宽 | 11 位 | — |
| `RC` payload | 22 B | — |

`RC` 帧的载荷**直接搬 CRSF 的 22 字节通道数据**（16 通道 × 11 位打包），RX 侧重建 CRSF 的帧头与 CRC8。只搬不解——解包重编要选位宽（省不下多少）、引入转换损耗，而 CRSF 的 11 位编码本身就是个稳定标准。

150 Hz、22 B 载荷下，27 字节帧在 0.975 Mbps 上约 222 us，占 6.67 ms 周期的 3.3%，余量充足；500 Hz 档（2 ms 周期）就是 11%。

### 2.5 分片规则

- `MORE` 置位表示后面还有分片。
- 接收端**严格按 `seq` 顺序重组**。
- 出现缺口、或超过 100 ms 未收齐，**丢弃整段**（超时值见 3.6）。
- 不做乱序重组：显式分片头（`frag_idx` + `frag_total`）每包要多付 2 B，代价大于收益。

### 2.6 空口开销核算

以 22 字节载荷、FLRC 1.3 Mbps（有效 0.975 Mbps）为例：

| 组成 | 字节 | 空口（估算） |
| --- | --- | --- |
| header + seq + payload | 25 | 约 205 us |
| 加 4 B tag（P1/P2） | 29 | 约 238 us |
| 前导码与同步字 | — | 再加几十 us |

tag 的代价约 16%，前导码与同步字是固定开销，速率越高占比越大。这些数字按有效速率线性折算，属于量级估算。

### 2.7 链路质量与诊断

**不另建诊断通道，复用 CRSF 既有的字段。** CRSF 自带一个链路统计帧（`0x14` LINK_STATISTICS），字段正好覆盖我们需要的：

| CRSF 字段 | 我们的来源 |
| --- | --- |
| 上行 RSSI | RX 测得的接收强度 |
| 上行 LQ | RX 侧"收到 / 应收"的成功率 |
| 上行 SNR | RX 测得 |
| 下行 RSSI / LQ / SNR | TX 侧自己测 |
| RF 模式 | 当前速率档 |

于是有两个生成点：

- **RX 到飞控**：用自己测到的上行质量组装
- **TX 到遥控器**：下行质量自己测，上行质量从遥测里取

这意味着**遥测回程里必须带上 RX 侧的链路质量**（LQ、RSSI、SNR、当前档位）。这是 `TLM` 帧要承载的内容之一。

速率自适应取其中的 LQ（见 4.5），动态功率取 RSSI 与 LQ（见 4.6），都不另外采一套。具体字节布局以 CRSF 规范为准，不在这里重述。数据链路的溢出与丢弃字节数没有现成的 CRSF 字段承载，不上报。

## 3. 链路状态机

### 3.1 两条链路的关系

控制链路（sub-GHz）与数据链路（2.4G）各跑一份同样的状态机，互相独立。系统级的「在线」由控制链路决定：控制链路在即系统在线；数据链路掉线只降吞吐。

### 3.2 状态

| 状态 | 含义 |
| --- | --- |
| `UNCONFIGURED` | 没有 `root_key`，什么都不做 |
| `UNPAIRED` | 有 `root_key`，但没有配对记录 |
| `PAIRING` | 用户按下按键，正在配对 |
| `SEARCHING` | 有配对记录，正在尝试建立连接 |
| `CONNECTED` | 已建立连接，正常收发 |

`UNCONFIGURED` 与 `UNPAIRED` 的区别只影响对外提示，行为上都是「不参与」。

### 3.3 TX 侧转移

| 起点 | 事件 | 终点 | 动作 |
| --- | --- | --- | --- |
| `UNCONFIGURED` | 写入 `root_key` | `UNPAIRED` | 生成并保存 `dev_id` |
| `UNPAIRED` | 长按按键 | `PAIRING` | 降功率、切配对同步字、周期发 `PAIR_REQ` |
| `PAIRING` | 配对成功 | `SEARCHING` | 记录对端 `dev_id` 与两个 nonce、恢复功率、切常态同步字 |
| `PAIRING` | 超时 30 s | `UNPAIRED` | 恢复功率与同步字 |
| `SEARCHING` | 周期发 `BEACON`；收到 `SESS_RESP` 就算出会话、发 `SESS_CFM` | `CONNECTED` | 进入常态收发 |
| `CONNECTED` | 250 ms 收不到任何有效包 | `SEARCHING` | 继续发 `BEACON` |

### 3.4 RX 侧转移

与 TX 对称，差别是 RX 不主动发 `BEACON`，只监听：

| 起点 | 事件 | 终点 | 动作 |
| --- | --- | --- | --- |
| `UNCONFIGURED` | 写入 `root_key` | `UNPAIRED` | 生成并保存 `dev_id` |
| `UNPAIRED` | 长按按键 | `PAIRING` | 切配对同步字、监听 `PAIR_REQ` |
| `PAIRING` | 配对成功 | `SEARCHING` | 记录对端 `dev_id` 与两个 nonce、切常态同步字 |
| `SEARCHING` | 收到 `BEACON` 回 `SESS_RESP`；再收到本会话钥匙的 `SESS_CFM` | `CONNECTED` | 按 `BEACON` 的跳频索引对齐，进入常态 |
| `CONNECTED` | 100 ms 收不到有效包 | `SEARCHING` | 输出失控保护值 |

失控保护是 `CONNECTED` 之外的一个**输出行为**，不是链路状态：`SEARCHING` 期间 RX 必须持续输出预设的失控值给飞控，不能中断。

失控值由 **TX 侧配置、配对时下发给 RX 存本地**。默认「油门 0、其余通道中位」，可配置为「保持最后有效值」。

配对载荷的形状（`PAIR_REQ` / `PAIR_RESP` / `PAIR_CFM` 共用）：

```
[dev_a(4)][dev_b(4)][nonce_a(4)][nonce_b(4)][flags(1)][failsafe(22)]
```

`failsafe` 是 22 字节的 RC 通道载荷（与 CRSF 的通道帧同格式），只有发起方（TX）填：它设过值就置 `flags` 的 bit0，响应方收到后照单存本地并写 NVS；没置位就保持自己那份——免得被一串 0 覆盖成"所有通道最小值"。

载荷里的两个 nonce 不只管 `MAC_b` 的新鲜性：它们还参与 `pair_key` 派生（见 [05-security](05-security.md) 第 3 节），所以要连同对端 `dev_id` 一起落盘。

「保持最后有效值」是以后的选项，现在只有预设值这一种失控行为。

### 3.5 会话建立（三次握手）

与配对同一个形状：双方各出一个 nonce，都进 KDF，最后一条消息用新钥匙打 tag、回带对方的 nonce，证明两边算出了同一把钥匙。区别只是钥匙材料和生命周期——配对用长期共享的 `root_key`，会话用配对建立的 `pair_key`；配对材料要落盘，会话材料用完即弃。

TX 周期性在固定信道上发 `BEACON`，携带三样东西：

| 内容 | 作用 |
| --- | --- |
| `nonce_t` | 本次会话的随机数 |
| 信道 / 跳频信息 | RX 据此对齐；见第 5 节 |
| profile | 速率档、tag 开关、加密开关（RX 只校验一致，不跟随） |

握手三步：

1. TX → RX：`BEACON{version, profile, hop, nonce_t}`，用配对级 `link_auth` 认证。
2. RX → TX：`SESS_RESP{nonce_t, nonce_r}`，同样用 `link_auth` 认证；`nonce_r` 由 RX 现抽，回带 `nonce_t` 是为了让 TX 认出这是对哪一次请求的回应。
3. TX → RX：`SESS_CFM{nonce_r, hop}`，用**新会话钥匙**打 tag，并回带本端此刻的跳频索引。RX 验过它才采用会话。

会话钥匙 `KDF(pair_key, "zlrs/session", nonce_t || nonce_r || 发送方 id || 接收方 id)`：收发各一把，本机发用 out（本机 id 在前）、收对端用 in（对端 id 在前），见 [05-security](05-security.md) 第 3 节。采用会话时按确认帧里的跳频索引对齐（旧固件的确认只有 `nonce_r`，那一步退回用 `BEACON` 里那个），序列号从 0 起。（代码里这两个 nonce 是 `zlrs_link_t` 的 `sess_nonce_t` 与 `sess_nonce_r`。）

**为什么必须有第二步。** 只有 `nonce_t` 的话，钥匙完全由 TX 那个可被整帧重放的值决定：录一个旧 `BEACON` 重放，RX 就会重算出那次会话的钥匙、连序号窗口一起复位，旧录制的帧又能验证一遍。掺进 RX 现抽的 `nonce_r` 之后，重放只能换来一条全新钥匙的候选会话，而采用它需要 TX 拿同一把钥匙来确认——录制的旧帧一条都用不上。

**重传**：RX 对同一个 `nonce_t` 只重发同一条响应（`nonce_r` 不换）；TX 收到响应就回确认，收到重复响应就再发一次确认。丢哪一条都只耽误一个 `BEACON` 周期，不需要额外定时器。

**建链时机**：TX 发出确认即进 `CONNECTED`（这样双方从下一帧起一起推进跳频）；RX 验过确认才进 `CONNECTED`。对端没收到确认时，失联判定会把 TX 拉回 `SEARCHING` 重新握手。

`nonce_t` 在 TX 每次重启或重建链路时重抽，所以每次会话的密钥都不同。

`BEACON` 周期：控制链路 **每秒一次**，数据链路 **每 2 秒一次**。

**两条链路各自发自己的 `BEACON`，各自建立会话。** 数据链路不依赖控制链路，这样"一条断了不影响另一条"才真正成立。两条链路用的是同一套代码，只是参数不同。

握手要求 TX 在 `SEARCHING` 才能发 `BEACON`（那时跳频索引是冻结的，RX 采用 `BEACON` 里的索引才落得准）。**连接态也周期发 `BEACON`**（默认 1 s，`CONFIG_ZLRS_APP_RESYNC_PERIOD_MS`，见 5.1），所以数据链路虽然不判失联，也能靠它发现"对端换了会话"（重启、重新配对）并自动重新握手：对端重启后链路能自己回来，不需要本端也重启。关掉这个周期（周期设 0）就退回老行为——那时对端重启要等本侧重启或重新配对。

### 3.6 定时器

两条链路的严格程度不同：

| 项 | 控制链路 | 数据链路 |
| --- | --- | --- |
| 配对窗口 | 30 s | 30 s |
| 分片重组 | 100 ms | 100 ms |
| 失联判定 | RX 失控保护 100 ms / TX 250 ms | **无判定**（尽力而为，且空闲不发空帧；对端重启靠周期 `BEACON` 重握手，见 3.5 与 5.1） |
| `BEACON` 周期 | 1 s | 2 s |

分片重组超时给到 100 ms 是因为 ARQ 的重传周期是 30 ms：太短会在重传途中把半截分片丢掉（见 4.3）。

控制链路严格，因为它承载操控，必须知道对方在不在。数据链路宽松，因为它是尽力而为的辅助通道，"断了也无所谓"。

**全部按时间定义，不按包数**——这样换帧率不需要改参数。

## 4. 超帧与速率档

### 4.1 固定超帧

**每个控制周期形状完全相同。** 动态分配时隙能省下约 3% 的切换开销，代价是延迟上限不可算、出问题难定位；[01-overview](01-overview.md) 那条"确定性延迟、故障可预测可检测"的要求更值这 3%。

一个周期（150 Hz，6.67 ms）的形状：

| 段 | 内容 | 约计 |
| --- | --- | --- |
| 1 | sub-GHz：TX 发 `RC` 帧 | 238 us |
| 2 | sub-GHz：切收，RX 发遥测帧（**必须回应**） | 91 + 238 us |
| 3 | 切到 2.4G | — |
| 4 | 2.4G：数据窗口，前半 TX 到 RX，后半 RX 到 TX | 约 5.7 ms |
| 5 | 切回 sub-GHz | — |

控制链路加频段切换合计约 924 us，占周期的 14%。这里的数字是 1.3 Mbps 档、29 字节帧的粗估，参考 [03-architecture](03-architecture.md) 第 4 节。

**帧率是档位，不是常数。** 目前两档：150 Hz（默认，远距/通用）与 500 Hz（近距离竞速，`CONFIG_ZLRS_APP_CONTROL_RATE_HZ`）。实际生效值由启动时的**时间计划**算出来，受两个约束：

| 约束 | 例子 |
| --- | --- |
| 地区占空比 | EU868 的 1% 只撑得住约 46 帧/秒（1.3 Mbps、31 B 帧），500 Hz 会被压到 46 Hz 并告警 |
| 空中时间 | 窄带速率（0.325 Mbps）下，一帧要装下"发 RC + 收遥测"两个时隙，帧率上限约 470 Hz |

计划的内容：帧周期、每个时隙的等待预算（帧周期的四分之一，窄带时按实际空中时间放宽）、以及遥测/数据窗口的稀疏系数——控制帧率拉高以后，遥测与数据窗口不必跟着涨：遥测按 ~150 次/秒、数据窗口按 ~100 次/秒折算成"每 n 帧一次"（500 Hz 档就是 1/3 与 1/5）。稀疏化在链路层内部计数完成，两端同固件所以节奏一致，跳频不会失步。

再往上（1000 Hz）这套架构不够用：RAC 的排期粒度是毫秒，而每帧只剩 1 ms。**这不是换个 RAC 调用能解决的**——RAC 的 FLRC burst 是**单向批量传输**（一次事务把一大块数据拆成固定帧连续发、只有两个 TX FIFO 指针边发边填、带唤醒握手），`min_interframe_delay_us` 是"把帧间隔压到最小"的吞吐旋钮而不是 1 ms 节拍，事务起点仍由毫秒粒度的 planner 决定，也不提供收发交织与逐帧换频。1000 Hz 要的是**控制链路自己拥有射频**：IRQ 驱动的逐帧时序（直调驱动 + 硬件 auto-Tx/Rx），代价见 [10-roadmap](10-roadmap.md) 的 M4。

协议与时间计划这一侧已经按 1 ms 一帧钉住了（`link: 1000 Hz frame cadence`、`region: 1000 Hz plan`）：2.6 Mbps 档下 31 B 的 RC 帧是 108 µs，时隙预算 308 µs，四个时隙分得开；遥测与数据窗口的稀疏系数是 1/6 与 1/10。差的是射频后端——那部分要上板做（见 M4 的路径 A）。

### 4.1.1 调制按链路各自选

上面的 150 Hz / 6.67 ms 是**两条链路都跑 FLRC**时的形状。窄带地区（868 / 470 / 433）放不下宽带 FLRC 时改用 LoRa，这时调制是**按链路各自选**的，不是整机切换：

- 数据链路留在 2.4G 跑 FLRC（不受 sub-G 频段宽度影响）
- 控制链路在 sub-G 上跑 LoRa，进"远距档"：默认 **SF7 / BW125 / CR 4/5 / 8 符号前导**，配置档位 `CONFIG_ZLRS_APP_LORA_CONTROL_RATE_HZ`（默认 10 Hz）
- 超帧周期由**最慢的那条链路**决定：控制链路的 RC 帧与遥测帧加起来超过 100 ms 时，周期就按实际需要拉长

之所以不是"整机切 LoRa"：两条链路本来就是两个 RAC client，频段也不同，各自配自己的调制最省事，也保住了 2.4G 那一路的吞吐。

**时间常数不再写死。** 窄带地区的一帧是几十毫秒而不是亚毫秒，所以：

| 原来的常量 | 现在怎么来 |
| --- | --- |
| 速率档 = 一个速率 | `zlrs_mod_cfg_t`：调制 + 参数（FLRC 速率 / LoRa SF·BW·CR·前导码），见 `include/zlrs/proto/mod.h` |
| 空中时间 = 载荷 ÷ 速率 | `zlrs_mod_airtime_us()`：FLRC 沿用原模型，LoRa 按 Semtech 公式（`Ts = 2^SF/BW`，前导 `n + 4.25` 符号，载荷符号含 CR 与低速率优化） |
| 超帧时隙 | `zlrs_region_control_plan()` 按调制档算：帧周期至少装得下"RC + 遥测 + 给另一条链路的预留"，时隙预算的上限也跟着档位走（FLRC 2 ms 的经验上限对 LoRa 不适用） |
| ARQ 重传超时 | `zlrs_link_cfg_t.arq_timeout_ms`，由档位的空中时间派生（至少 30 ms） |
| LQ 窗口 | 本来就是按帧数（128 帧）而不是按时间，换档不用改 |

算出来的典型数字（SF7 / BW125 / CR 4/5、31 B 的 RC 帧）：RC 帧空中时间 **72 ms**，7 B 遥测帧 **36 ms**，两者加上余量是 108 ms —— 所以 10 Hz 的申请会被压到 **9 Hz**，超帧周期 111 ms。EU868 的 1% 占空比则连这一档都撑不住（一帧就 72 ms，每秒只够 0.14 帧），时间计划会压到 1 Hz 并告警：这是法规结论，不是可以调参绕过的。

### 4.2 遥测窗口

**RX 必须回应**，即使这一周期没有任何遥测数据，也要发一个最小的空帧（`header` + `seq` + `tag`，约 7 B，空口约 57 us）。

理由：TX 靠"这个周期收到东西了吗"判断链路存活。如果 RX 只在有遥测时才发，TX 就无法区分"链路断了"和"暂时没数据"，失联判定会失效。

### 4.3 数据窗口

数据窗口**固定对半分**：前半 TX 到 RX，后半 RX 到 TX。时序最可预测；单向流量时会浪费一半，但数据链路本来就是尽力而为，接受这个代价。

**不发空帧。** 数据链路不做失联判定，见 3.6——空闲时没有帧可发，判了就会把"暂时没数据"当成断链、反复重建会话。代价是对端重启后要等本端重启、重新配对或收到周期 `BEACON`（见 3.5）。

数据链路的默认 profile 是 **best-effort**：裸字节流，缓冲满即丢，附溢出计数。理由：透传的典型用途（MAVLink 遥测流）对延迟敏感、对丢包容忍，而且上层协议往往自带重传。ARQ 作为可切换档保留。

ARQ 档的实现要点（见 `include/zlrs/link/link.h` 与 `lib/link/link.c`）：

- 载荷头 2 字节是数据序号，接收端按它去重、按序投递；确认用**累计 ACK**（ACK 帧带"已按序收到哪个序号"）
- 发送窗口 4 帧、超时 30 ms 重传、最多 6 次。窗口是"从队首开始连续的若干帧"，只有收到 ACK 才把字节从队列里提交，所以重传不需要额外缓存
- 重传用尽：这一段计成丢弃（可见计数），窗口清空、序号重开，并**发一次重同步**让接收端把半截消息作废——否则后面的数据会被拼到带洞的流上
- 会话里的第一帧必须从序号 0 开始：宁可丢一段，也不能把半截流错位投递给上层

**帧长动态**，上限为 `min(255, 当前速率档下半个窗口能装下的字节数)`。每帧都要付固定开销（前导码 + 同步字），短帧的吞吐只有长帧的四分之一左右：

| 帧长 | 单帧空口（含前导/同步） | 单向吞吐 |
| --- | --- | --- |
| 29 B | 约 287 us | 约 43 kB/s |
| 128 B | 约 700 us | 约 110 kB/s |
| 255 B | 约 1100 us | 约 175 kB/s |

（2.6 Mbps 档、每周期单向 2.85 ms 的粗估。）

但**一帧必须在窗口内发完，不能跨窗口**，否则时序会乱。所以低速档下长帧反而装不下，上限必须跟着速率档走：

| 速率档 | 半窗口能装下 |
| --- | --- |
| 2.6 Mbps | 约 695 B |
| 1.3 Mbps | 约 348 B |
| 0.65 Mbps | 约 174 B |
| 0.325 Mbps | 约 87 B |

### 4.4 速率自适应

**两条链路都自适应，但目标函数不同：**

| 链路 | 目标 | 质量退化时的行为 |
| --- | --- | --- |
| 控制链路 | 距离与稳定性 | **降速率档**换灵敏度，接受帧率下降 |
| 数据链路 | 帧率与吞吐 | 优先保住速率与帧率，不为距离而降速 |

所以速率档不能只是一个速率值——降速会让单包空口变长，150 Hz 的周期可能装不下。**档位是「频段 + 速率 + 帧率」的组合**。

数据链路的速率档上限由**配置的串口波特率**推导：用户设 115200，链路就要能扛住约 11.5 kB/s；设 921600，就是约 92 kB/s。配置工具负责校验这个目标在当前配置下是否可达。这样用户不需要凭空估"峰值带宽"。

### 4.5 自适应判据

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 主判据 | 每档的 LQ 下限（`min_lq_to_stay`） | 链路质量的地面真相：滑窗成功率 |
| 升档余量 | 比目标档的下限再高 10 个百分点（`hysteresis`） | 阈值附近不横跳 |
| 连续窗口 | 3 个（每次评估 1 s，见下） | 单次样本太抖 |
| 换档后保持 | 2 s（`hold_ms`）内不评估 | 换档后链路要时间稳定 |
| 升档 | 升上去之后仍要连续窗口达标，否则降回来 | 比"条件满足直接升"稳 |

评估在 1 Hz 的上报里做（`report()`，见 `app/src/main.c`），拿的是控制链路的 `lq_percent`；**RSSI 不参与速率判定**，它只进动态功率那条路（见 4.6）。

### 4.6 发射功率（动态功率）

速率不是唯一的旋钮：**功率**同样决定链路预算，而且改功率比改速率便宜得多（不改变帧时长，不影响超帧形状）。策略与速率自适应共用一套骨架，依据是 RX 通过遥测回报的**上行 RSSI 与 LQ**（见 4.2）：

| 条件 | 动作 |
| --- | --- |
| RSSI 低于下限（默认 −95 dBm）**或** LQ 低于下限（默认 90%） | 连续 3 次评估后升一档（步长 3 dB） |
| RSSI 高于上限（默认 −70 dBm）**且** LQ 高于上限（默认 98%） | 连续 3 次评估后降一档 |
| 两者之间 | 不动（滞回区，避免阈值附近来回跳） |
| 两次调整之间 | 至少保持 2 s |
| **一秒内没收到遥测** | 直接回到上限——那一头多半掉线了，先打满再谈省电 |

判据**每秒评估一次**（不是每个遥测帧评估一次）：遥测是 150 Hz 灌进来的，按帧评估的话"连续 3 个样本"只有 20 ms，等于没滤波；按秒评估才是"连续 3 秒"。

上下限：上限取"配置功率与地区上限的较小值"（法规优先级最高，见 5.2），下限是配置项（默认 0 dBm）。起手用上限：没拿到遥测之前没有降功率的理由。

与 ELRS 的动态功率是同一个思路，差别在于我们的判据直接来自 RX 的遥测回报（8 字节 TLM 里的 RSSI/LQ），不需要额外的统计通道。默认开启（`CONFIG_ZLRS_APP_DYNAMIC_POWER=y`），阈值与滞回按实测曲线标定（见 [10-roadmap](10-roadmap.md) 的 M4）。

## 5. 跳频策略

**采用逐包跳频（每包换一个频点）**：索引由 `fhss_seed` 派生的频点表决定，TX 在 `BEACON` 里携带跳频索引，RX 按同一张表与之锁步（时隙相位由超帧结构本身决定）。

这样同时买到抗干扰能力、与其它 zlrs 链路的共存能力，以及法规跳频条款所需的信道数与驻留时间。代价是收发时序必须按「每包一个时隙」建模，而不是「一直开着收」：RX 在特定时刻打开特定频点。

### 5.1 逐包跳频的前提

四个前提，缺一不可：

| 前提 | 来源 |
| --- | --- |
| 共同的频点表 | `fhss_seed` 派生（两端各自算） |
| 共同的时隙长度 | 速率档决定 |
| 共同的索引 | `BEACON` 携带，建链时对齐，连接态每个周期再对齐一次 |
| 时钟漂移的处理 | **连接态周期 `BEACON` 重同步**：RX 直接把索引设成 `BEACON` 里那个（两端帧计数一致，理论上只差漂移量），漂移累积被每个周期抹掉一次 |

最后一条是最难的地方：两端晶振有偏差，跑一段时间后 RX 就会"踩空"。做法是连接态也周期发 `BEACON`（`CONFIG_ZLRS_APP_RESYNC_PERIOD_MS`，默认 1000 ms，0 = 关）：每 `n` 帧（`n = 周期 / 帧周期`）算一个**重同步帧**，这一帧两个时隙都落在同步信道上——TX 发 `BEACON`，RX 在这一帧收，收到就把索引设成对端报的那个，顺手把"对端还在"的时间戳刷新。

重同步帧上的 `BEACON` 是配对级 `link_auth` 打的 tag，录下来的旧帧也能验过，所以收下它有两道门：

- **序号必须更新**：同会话的 `BEACON` 与数据帧共用一个序号空间，旧帧的序号过不了这一关；
- **换会话要"最近完全听不到对端"**：`BEACON` 里的 `nonce_t` 与本端会话不一致时，只有在 `now - last_rx > beacon_period` 时才认（对端重启），否则当重放丢掉。这条同时是**对端重启后自动重连**的实现：TX 重启 → 新 `nonce_t` → RX 退回 `SEARCHING` 回 `SESS_RESP` → TX 用 `SESS_CFM` 把索引一起带回来；RX 重启 → 它自己就是 `SEARCHING`，听到周期 `BEACON` 就走同一条路。

关掉周期重同步（0）就回到"只在建链时对齐"：省掉这一帧的开销，代价是长时间跑会因漂移丢包、对端重启后要等本侧重启或重新配对。

### 5.2 法规约束

跳频参数由目标地区决定：

- FCC 15.247 的跳频条款要求 ≥50 个信道、单信道驻留 ≤400 ms、各信道等概率使用。逐包跳频与慢跳频都满足；固定信道不满足，只能走非跳频的功率限制条款。
- ETSI EN 300 220 的某些子频段有占空比限制（1% / 10%），这会直接限制控制帧率与透传可用的时隙比例。
- 2.4G ISM 无跳频要求，宽松得多。

所以需要一层**地区配置**，把信道表、功率、占空比上限参数化。板级 dtsi 已经按这个思路分频段给功率表（`tx-power-cfg-lf` / `tx-power-cfg-hf`），地区配置沿用同一模式即可。

实现在 `lib/region`：四张表（FCC915 不限占空比、EU868 1%/60 s、CN470、CN433），启动时做自洽校验——**地区要的 sub-G 硬件与板子一致**（HF SKU 跑 868/915，LF SKU 跑 470/433，不匹配就红灯告警且不发射频）、信道表在频段边界内、功率不超上限——发射前再做占空比记账，额度用完的时隙直接让出去并计数。法规是硬约束，不是性能调优项。

信道间隔按**调制带宽**定，不照抄 LoRa 的信道规划：CN470 用 300 kHz 间隔（96 信道），CN433 只有 1.74 MHz 宽、放得下 5 个 300 kHz 信道。窄频段地区因此带 `max_rate_bps`，配置超过上限会自动压到 0.325 Mbps 的窄带档（FCC915 不限）。

想要更高吞吐或更长距离时，这些地区可以改用 LoRa 等窄带调制（见 4.1.1），但**这不是改参数**：速率档表要变成"调制 + 参数 + 空中时间模型"，超帧时隙、ARQ 超时、LQ 窗口这些跟着调制时间预算派生的常数都要重推。见 [10-roadmap](10-roadmap.md) 的 M4。

### 5.3 前导码与同步字

- FLRC：同步字固定 **4 字节**，三个槽（控制 1 / 数据 2 / 配对 3）由配对钥匙按角色派生，见 `lib/link/link.c` 的 `derive_pair()`。
- LoRa：同步字只有 **1 字节**。另开一条派生标签（`zlrs/sync/lora/control` 与 `.../data`），取 1 字节并把最高位当 private bit 置 1——这样高 4 位不会是 0，满足 LR20xx "`0x0X` 不能用"的约束。配对阶段还没有配对钥匙，派生不出来，LoRa 的配对帧固定落在私网同步字 `0x12`（`LORA_PRIVATE_NETWORK_SYNCWORD`），配对一完成就换成派生值。
- 前导码在 datasheet 给出的最小值之上留余量（LoRa 默认 8 个符号；SF5/SF6 建议 ≥12 符号）。

两种调制的同步字各派生各的，互不借用：4 字节的那套不截断给 LoRa 用，1 字节的那套也不参与 FLRC。
