# 安全模型：身份、配对与密钥

本文定义 zlrs 的安全模型：谁能连、怎么建立、密钥从哪来、挡得住什么。

设计约束：不做产线、不用全局公共密钥、用户自己配密钥、多台设备共享根密钥但同一时刻只有已配对的两台能通。

## 1. 结论摘要

- 身份层分两级：**信任域**（根密钥，多台共享）与**配对**（决定当前是哪两台在通）。
- 根密钥不是链路凭据，而是**配对的授权凭据**。
- **同一时刻只保留一个配对**，换绑靠重新配对。
- **配置走有线**（每台设备一次，写入根密钥），**配对走空中**（按键触发）。
- 配对是按键触发的三次握手：只交换设备标识与两个随机数并互相认证，空中不传任何密钥。
- 设备身份由首次启动时的 RNG 自行生成，**不需要产线**。

## 2. 数据

| 名称 | 长度 | 来源 | 可见性 |
| --- | --- | --- | --- |
| `root_key` | 32 B | 用户配置（配置工具写入） | 保密 |
| `salt` | 16 B | 固定常量，含 KDF 版本号（如 `zlrs/kdf/v1`） | 公开 |
| `dev_id` | 4 B | 首次启动 RNG 生成 | 可公开 |
| `pair_salt` | 8 B | 配对时双方各出一个 nonce | 可公开 |
| `pair_key` | 32 B | 配对时派生，不存储（用 `dev_id` 与 `pair_salt` 重算） | 保密 |

`dev_id` 与 `pair_salt` 存 NVS（配对记录，见第 4 节），配对时明文交换，所以都不算秘密；冒充 `dev_id` 需要先过 MAC 认证。未配置 `root_key`（全零）的设备不参与任何配对，也不接受数据。

## 3. 派生结构

```
root_key (32B, 用户配置, 组内共享)
  auth_key = KDF(root_key, "zlrs/auth")                  -> 配对握手认证
  pair_key = KDF(root_key, "zlrs/pair", sort(dev_id_a, dev_id_b) || sort(nonce_a, nonce_b))
    fhss_seed = KDF(pair_key, "zlrs/fhss")[:4]           -> 跳频表种子
    sync_ctrl = KDF(pair_key, "zlrs/sync/control")[:4]   -> sub-GHz 同步字
    sync_data = KDF(pair_key, "zlrs/sync/data")[:4]      -> 2.4G 同步字
    link_auth_ab = KDF(pair_key, "zlrs/link-auth", dev_id_a || dev_id_b)  -> 每包 tag
    link_auth_ba = KDF(pair_key, "zlrs/link-auth", dev_id_b || dev_id_a)  -> 反向那把
    session_ab   = KDF(pair_key, "zlrs/session", nonce_t || nonce_r || dev_id_a || dev_id_b)
    session_ba   = KDF(pair_key, "zlrs/session", nonce_t || nonce_r || dev_id_b || dev_id_a)
                                                          -> 每次会话重算的一对
    link_enc  = KDF(pair_key, "zlrs/link-enc")            -> 可选加密（P2，未实现）
```

链路层只接触派生值，不直接接触 `root_key`：换 KDF、加前向保密、改密钥长度都不影响协议本身。

`pair_key` 的上下文是**排序后**的双方 `dev_id` 加**排序后**的两个配对 nonce。排序让两端各自算一次就得到同一个值；nonce 让"这一对设备"与"这一次配对"分开——每次配对换一份 `pair_salt`，下面整棵子树都跟着换，旧配对的录制作废。代价是 `pair_salt` 要落盘，否则重启后算不出同一把钥匙。

`link_auth` 与 `session` 各是一对钥匙，方向由双方 `dev_id` 的先后顺序表达：本机发出的帧用 out（本机 id 在前），校验对端帧用 in（对端 id 在前）。两端各算一次就配成对，不需要协商，标签里也不掺角色。两个方向共用一把的话，把自己发出的帧打回自己会被当成对端帧收下（反射），见第 7.2 节。

`link_enc` 还没实现；做的时候方向与 CTR 计数器要一起设计，别两个方向共用一把钥匙加同一套计数器。加密同样走 PSA（AES-CTR），在 Kconfig 里打开对应的 `PSA_WANT_*`。

上空中出现的三个值（`fhss_seed` 与两个同步字）都是 `pair_key` 的单向派生值，听到也推不出密钥。ELRS 直接把 UID 发出去，等于把凭据发出去。

## 4. 配对流程

前提：两端都已配置同一个 `root_key`，且两端都物理进入配对模式（按键长按），配对期间使用最低发射功率。

1. TX 长按按键进入配对模式并降到最低功率；RX 同样长按进入配对模式。
2. TX 发 `PAIR_REQ`，携带 `dev_id_a`、`nonce_a` 与 `MAC_a`。
3. RX 校验 `MAC_a`，记下 `dev_id_a`，生成 `nonce_b`，回 `PAIR_RESP`（带 `dev_id_b`、`nonce_b` 与 `MAC_b`）。
4. TX 校验 `MAC_b`，记下 `dev_id_b`；双方各自派生 `pair_key` 及其派生值。
5. TX 发 `PAIR_CFM`（携带 `MAC_c`）；RX 校验后记下配对、退出配对模式。
6. TX 记下配对、退出配对模式，恢复功率，进入常态。

两端落盘的是对方的 `dev_id`、配对时的两个 nonce（`pair_salt`）与配对状态。

```
MAC_a = MAC(auth_key, "zlrs/pair/req"  || dev_id_a || nonce_a)
MAC_b = MAC(auth_key, "zlrs/pair/resp" || dev_id_b || nonce_a || nonce_b)
MAC_c = MAC(auth_key, "zlrs/pair/cfm"  || dev_id_b || nonce_b)
```

MAC 里同时包含两个 nonce，因此无法重放旧握手；三条消息带各自的标签、收发角色由状态机把着，所以配对握手不需要方向钥匙。两端都已经有 `root_key`（第 10 节），配对**不传输任何密钥**：只认证 `dev_id` 并交换两个 nonce。

### 规则

- 配对模式必须**物理按键**进入，且超时自动退出（30 s）。
- 常态下设备**拒绝一切配对握手**，所以无法被远程抢占（换绑只能靠物理按键）。
- 配对成功即**替换**原有配对（同一时刻只保留一个）。
- 换绑靠一次新的配对握手：新记录顶掉旧记录，另一端在下一次配对或超时后失效。
- 同一时刻多台 RX 处于配对模式时先响应者胜出。所以配对时只给目标 RX 上电，或利用贴身低功率把覆盖范围压到最小。

状态机与消息格式见 [02-protocol.md](02-protocol.md) 3.3/3.4。

## 5. 会话建立（与配对区分）

配对决定"和谁通"，会话决定"这一次用什么钥匙"：`pair_key` 在配对时两端各自就算好（第 3 节），会话只给它换一对每次都不同的 nonce，不改持久状态、不需要用户参与。流程与消息格式见 [02-protocol.md](02-protocol.md) 3.5，这里只说安全性质：

- **双方各出一个 nonce**：TX 出 `nonce_t`（`BEACON` 携带），RX 出 `nonce_r`（`SESS_RESP` 携带），两个都进会话钥匙。只靠 TX 那个可被整帧重放的值是不够的——录一个旧 `BEACON` 重放，RX 就会重算出那次会话的钥匙。
- **采用会话要等确认**：TX 用新钥匙打一条 `SESS_CFM`，RX 验过才采用。重放的旧帧用的是当时的 `nonce_r`，跟这次现抽的对不上，一条都进不来。
- **只换流密钥，不换身份**：会话重算不动配对记录，也不动"只认已配对 `dev_id`"这条规则；`nonce_t`、`nonce_r`、会话密钥与序号都不落盘，掉电即失效。
- **`BEACON` 用配对级的 `link_auth` 认证**：nonce 虽然公开，别人造不出能过校验的会话消息。

## 6. 对空中格式的影响

- **帧里不带任何身份字段**：过滤全交给射频同步字（常态 `sync_ctrl` / `sync_data`，配对模式用槽 3 的公开常量），不匹配的包在射频层就被丢弃，MCU 不会被唤醒。
- 跳频表由 `fhss_seed` 生成，两端各自算，不需要在空中同步种子本身。
- 每包带序列号（防重放）与 4 B tag（是否携带由 profile 决定，不由标志位决定）；方向不在帧里，在 tag 钥匙里（第 3 节）。
- 配对握手使用独立的包类型，只在配对模式下接收。

同步字与帧格式的细节见 [02-protocol.md](02-protocol.md) 1.1 与第 2 节。

## 7. 安全性质与已知弱点

### 7.1 对手模型

| 级别 | 对手 | 能力 |
| --- | --- | --- |
| L1 | 同场飞友 | 误占频段；基本不可能知道你的短语 |
| L2 | 有 SDR 的爱好者 | 录包、重放、伪造、逆向固件 |
| L3 | 有组织的攻击者 | 长期监听、侧信道、社工 |

**本设计针对 L1 与 L2，明确不防 L3**：不做前向保密（要做得在会话建立时加临时 ECDH），并接受"知道 `root_key` 的人能在配对窗口抢走配对"。对 L1/L2 而言，伪造一个包需要先破 HMAC-SHA256，现实中不可行。

### 7.2 分层

| 威胁 | 谁 | 靠什么挡 |
| --- | --- | --- |
| 组内其它设备误占链路 | 有 `root_key` 的自己人 | 配对记录 + 逐对密钥 |
| 外部攻击者伪造/占用 | 没有 `root_key` | 每包 tag、会话 nonce |

第一类**用密码学挡不住**：组内设备本来就持有 `root_key`，`pair_salt` 又是明文交换的，参与过或听过那次配对就能算出这一对的全部钥匙。拦住日常互扰的是"只认配对时记下的 `dev_id`"这条本地规则——配对的作用是限制**合法设备之间**的互扰，不是对抗攻击者。

**能防：**

- 不同用户之间的碰撞与误占（跳频种子与同步字都像随机数）
- 未配对设备占用链路，即使它知道 `root_key`
- 报文伪造与重放（序号 + 会话握手，旧 `BEACON` 重放拿不到旧钥匙）
- 反射（把自己发出的帧打回自己）
- 换绑后旧录制作废
- 配对过程中的中间人

**防不住**：

- **`root_key` 泄露**：拿到根密钥的人可以主动与任何同组设备配对，顶掉你原来的配对。缓解手段是配对要物理接触加按键，攻击者得在你按下的窗口内靠近。
- **没有前向保密**：根密钥泄露后，过去录下的加密流量可被解开。要解决得在连接握手里加临时 ECDH；本设计接受这个代价。
- **同一根密钥的成员之间可以互相冒充，换绑也不吊销听过新配对的旧对端**：配对 nonce 是明文交换的，谁在场谁知道；要真正吊销只能换 `root_key`。
- **撤销只能逐台做**：丢设备时要在另一端重新配对一次，而不是吊销密钥。

## 8. 参数与算法

- 用户输入形式：**短语**；最小 12 字符，低于 16 字符给强度提示，配置工具支持一键生成。
- 加密：**默认关闭**，按 profile 打开（见下与 [02-protocol.md](02-protocol.md) 2.3）。
- MAC 算法：**HMAC-SHA256 截断到 4 B**，让 PBKDF2 / HKDF / MAC 全落在 SHA-256 一族，P1 不必引入 AES；只有 P2（加密）才需要 AES-CTR。
- KDF：**放在设备侧**，理由见下；salt 是**固定常量**，含版本号，不保密。
- RX 的密钥来源：**有线配置**（第 10 节）。

### 加密默认关闭

**机密性可以下放，认证不能**：

| | 能否下放到应用层 | 原因 |
| --- | --- | --- |
| **机密性**（加密） | 能 | 应用层若已端到端加密，链路层再加密是重复开销 |
| **完整性 / 来源** | **不能** | 见下 |

1. **控制链路没有"应用层"可以托管。** RC 帧是 TX 固件自己产生的，链路层不认证就等于谁能往空中发 RC 帧谁就能控制飞机。
2. **同步字是过滤器，不是凭据。** 它空中明文传输，攻击者收一包就学到，然后就能用它伪造包。
3. **应用层加密挡不住注入。** 解密出来发现是垃圾时，包已经进了接收窗口。

所以 **tag 必须有，加密可以默认关**（P1）。加密保留为可选档（P2），给"透传载荷本身没有加密"的场景用——裸 MAVLink、原始串口数据；配置工具要让用户明确选择。

### PBKDF2 迭代次数

迭代次数取 100,000，对应目标 MCU 上约 1–2 秒。**它随 KDF 版本号发布，发布后不能原地修改**：改了之后同一个短语会派生出不同的 `root_key`，新旧固件的设备就通不了。所以 `salt` 里必须含 KDF 版本号（`zlrs/kdf/v1`），将来调整迭代次数是**发一个新版本**，配置工具要允许选版本。否则某次固件升级后所有设备都得重新配置、重新配对，而用户不会知道为什么。

### salt 固定

盐防预计算，但"同一个短语在两台设备上导出同一个密钥"要求两端用**同一个**盐，所以盐不能每台随机生成。随机盐的代价是以后加设备必须同时知道那个盐，丢了盐就得全部重配；而它对弱短语也救不了场——攻击者针对单台设备枚举字典，和针对固定盐预计算一次，在弱口令面前是同一个量级。所以用**固定的、随协议版本走的公开盐**，把防护放在迭代次数和短语长度上；盐在这里是卫生性的：让 zlrs 的哈希空间与其它应用区分开。固定盐意味着所有用户共享同一张预计算表的暴露面，用高迭代次数与短语长度补偿。

### 算法选型

| 用途 | 算法 | 备注 |
| --- | --- | --- |
| 短语 → 根密钥 | PBKDF2-HMAC-SHA256 | 固定 salt + 高迭代；必须走 KDF，不能用裸哈希 |
| 根密钥 → 派生值 | HKDF-SHA256 | info = 标签，需要时再接上下文 |
| 每包 tag | HMAC-SHA256 截断 4 B | 覆盖 header + seq + payload |
| 可选加密（P2） | AES-CTR | MAC 覆盖密文（encrypt-then-MAC） |

设备侧原语走 Zephyr 的 **PSA Crypto**（`lib/proto/crypto_psa.c`，provider 通常是 mbedTLS；换带硬件加速的 provider 不用改应用）。主机侧测试没有 PSA，用一份同接口、零依赖的纯 C 实现（`tests/host/crypto_soft.c`）。两边必须给出同一串字节——主机侧用一组固定向量把它钉住。接口是薄封装（`include/zlrs/proto/crypto.h`）。

### KDF 放在设备侧

1. **派生规则唯一**：任何配置器送同一个短语进设备都必须得到同一个密钥，各家工具各自实现 KDF 就会互不兼容（ELRS 正是靠"推导在固件里"才有这个性质）。
2. **参数不被工具削弱**：迭代次数、salt、标签由固件定义，第三方工具改不了。

代价是设备要跑 PBKDF2，但这只在**配置那一刻**发生一次，不是每次启动——前提是设备只存派生后的密钥，不存短语。

## 9. 分层边界

协议核心不接触短语，也不接触 `root_key`，只接收派生好的 `fhss_seed`、两个同步字、按方向分开的 `link_auth` / `link_enc`，以及派生它们的输入（双方 `dev_id` 与 `pair_salt`）；会话密钥在链路层内按 `nonce_t` 与 `nonce_r` 现算。

## 10. RX 如何取得根密钥

第 4 节的配对流程假设**两端都已经有同一个 `root_key`**，这是与配对分开解决的另一个问题：

| 事件 | 何时发生 | 怎么传 |
| --- | --- | --- |
| **配置**（写入 `root_key`） | 每台设备一次 | 有线，见下 |
| **配对**（记录 `dev_id` 与 `pair_salt`） | 需要换绑时 | 空中，按键触发 |

### 配置方式：有线写入

新设备接一次串口，由配置工具写入 `root_key`（以及首次生成的 `dev_id`）。好处是之后所有配对都是**有认证的**，没有"首次信任"窗口，也不需要解释 TOFU；对 DIY 场景而言，本来就要焊板子、刷固件，接一次串口是自然的步骤。代价是每台新设备都要接一次线（**换绑不需要**——配对走空中按键，装进机身之后仍可重新配对），首次使用比 ELRS 的"上电即可绑定"多一道工序。

### 配置通道

**配置协议跑在数据通路上**：数据 UART 以及 USB 的数据 CDC，TX 与 RX 完全一样。同一条通路要和透传数据争用，靠工作模式分开：

| 时机 | 行为 |
| --- | --- |
| **开机时按住按键** | 进入配置模式 |
| **数据口魔数 / shell（无按键的板子）** | 进入配置模式，见 [01-system.md](01-system.md) 2.1 |
| **开机后长按按键** | 配对 |

正常运行时数据通路是透传口；进入配置模式后透传暂停、改跑配置协议。"进入配置模式"是个**不可远程触发的物理动作**（魔数只能从本地数据口送），这一点对安全有实际好处。

### 配置协议的帧与命令

```
[0xA5][0x5A][ver=1][cmd][len][payload][crc8]      crc 覆盖 ver..payload
```

主机发：状态查询、触发配对、写根密钥（64 个十六进制字符）、写短语、写失控值（22 字节 CRSF 通道载荷）、改数据口波特率、退出。设备回 `ACK`（带原命令与状态码）或 `STATUS`（16 字节：角色、链路状态、标志、`dev_id`、`peer_id`、LQ、本机 sub-G 硬件；报 SKU 是为了让工具一眼看出"刷错变体了"）。参数不合法、落盘失败、命令不认识都如实回状态码。

两条与安全相关的规则：

- **短语的派生规则固定在设备侧**（salt 与迭代次数由固件定），配置工具只送短语：第三方工具没法用弱参数派生，新旧固件的派生结果也一致。
- **配置模式没有远程入口**：只能靠按键或本地数据口魔数进入，运行时数据口只是透传口。

仓库里带一个最小的命令行工具 `scripts/zlrs-config.py`（读状态、触发配对、写密钥或短语、写失控值、改波特率、退出；`--self-test` 校验组帧与固件一致），任何第三方工具按同样的帧格式说话都能用。不设专门的控制口是有意的——TX 和 RX 流程完全相同，用户只需记一套操作；代价是 TX 运行时也不能边透传边配置。配置模式在超时（默认 300 s）或收到退出指令后结束。
