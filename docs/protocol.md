# 空中格式与链路状态机（粗排）

本文是第一版草案，用来把形状定下来，细节留待实测后再收。
身份与密钥见 [identity.md](identity.md)，射频栈见 [threading.md](threading.md)。

## 1. 物理层已经给了什么

设计帧之前先明确哪些不用自己做——LR2021 通过 RAC 已经提供：

| 能力 | 硬件提供 | 我们要做的 |
| --- | --- | --- |
| 前导码 | 是（`agc_pbl_len`） | 按速率档选长度 |
| 同步字 | 是（FLRC 支持 32 位） | 用它做第一级过滤，见 1.2 |
| CRC | 是（`SetFlrcPacketParams`） | **不需要自己加 CRC** |
| 长度字段 | 是（变长包格式） | 不需要自己带长度 |

结论：**帧里不要重复携带 CRC 和长度**，这两样是射频链路层的活。

### 1.2 用同步字替代 payload 里的 pair_id

**已定：帧里不放 `pair_id`，改用同步字做过滤。**

同步字是硬件匹配的：不匹配的包在射频层就被丢弃，MCU 根本不会被唤醒。
FLRC 提供 3 个同步字槽（每个 2 或 4 字节），接收端可配置为「匹配 1 或 2 或 3」。
分配如下：

| 槽 | 值 | 用途 |
| --- | --- | --- |
| 1 | `KDF(pair_key, "sync/control")[:4]` | sub-GHz 控制链路 |
| 2 | `KDF(pair_key, "sync/data")[:4]` | 2.4G 数据链路 |
| 3 | 公开常量 | 配对模式 |

这带来一个很强的性质：**配对之后，本机在物理层就听不到其它配对的流量**，
不消耗任何 MCU 时间或空口字节。

代价：切换频段时要连同步字一起重配（本来就要改频率，顺带做掉，不是额外开销）；
配对改变后要重新计算，一次性的。

速率档不编码进同步字——两端本来就必须处在同一速率才能通信，同步字不必重复
表达这个信息。

## 2. 帧格式

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `header` | 1 B | 高 6 位 = 类型（64 种），低 2 位 = 标志 |
| `seq` | 2 B | 会话内递增，防重放、用于分片重组 |
| `payload` | 0..N B | 类型相关 |
| `tag` | 0 或 4 B | MAC 截断，覆盖 header + seq + payload |
| `crc` | 硬件追加 | 由射频链路层生成与校验 |

`tag` 是否存在、载荷是否加密，由 **profile 决定，不由标志位决定**。否则攻击者
只要清掉标志位就能把认证降级掉。

profile 由 TX 在 `BEACON` 里声明，RX 跟随——TX 是链路的权威方。

### 2.1 header 标志位

| 位 | 名称 | 含义 |
| --- | --- | --- |
| 0 | `MORE` | 分片未结束 |
| 1 | `ACK_REQ` | 请求对端确认 |

### 2.2 包类型

6 位类型空间共 64 种，当前占用 10 种，留有余量。

| 值 | 类型 | 方向 | 说明 |
| --- | --- | --- | --- |
| 0 | `RC` | TX 到 RX | 遥控通道 |
| 1 | `TLM` | RX 到 TX | 遥测 |
| 2 | `DATA_UP` | TX 到 RX | 透传数据 |
| 3 | `DATA_DOWN` | RX 到 TX | 透传数据 |
| 4 | `ACK` | 双向 | 透传确认 |
| 5 | `BEACON` | TX 到 RX | 会话建立、跳频同步、profile 声明 |
| 6 | `PAIR_REQ` | TX 到 RX | 配对 |
| 7 | `PAIR_RESP` | RX 到 TX | 配对 |
| 8 | `PAIR_CFM` | TX 到 RX | 配对 |
| 9 | `CONFIG` | 双向 | 参数协商 |

### 2.3 空口开销核算

以 24 字节载荷、FLRC 1.3 Mbps（有效 0.975 Mbps）为例：

| 组成 | 字节 | 空口（估算） |
| --- | --- | --- |
| header + seq + payload | 27 | 约 222 us |
| 加 4 B tag | 31 | 约 254 us |
| 前导码与同步字 | — | 再加几十 us |

tag 的代价约 15%，前导码与同步字是固定开销，速率越高占比越大。
**这些数字都是按有效速率线性折算的估算，必须上板实测校正。**

## 3. 链路状态机

### 3.1 两条链路的关系

控制链路（sub-GHz）与数据链路（2.4G）各跑一份同样的状态机，互相独立。
系统级的「在线」由控制链路决定：控制链路在即系统在线；数据链路掉线只降吞吐。

### 3.2 状态

| 状态 | 含义 |
| --- | --- |
| `UNCONFIGURED` | 没有 `root_key`，什么都不做 |
| `UNPAIRED` | 有 `root_key`，但没有配对记录 |
| `PAIRING` | 用户按下按键，正在配对 |
| `SEARCHING` | 有配对记录，正在尝试建立连接 |
| `CONNECTED` | 已建立连接，正常收发 |

`UNCONFIGURED` 与 `UNPAIRED` 的区别只影响对外提示，行为上都是「不参与」。

### 3.3 TX 侧转移

| 起点 | 事件 | 终点 | 动作 |
| --- | --- | --- | --- |
| `UNCONFIGURED` | 写入 `root_key` | `UNPAIRED` | 生成并保存 `dev_id` |
| `UNPAIRED` | 长按按键 | `PAIRING` | 降功率、切配对同步字、周期发 `PAIR_REQ` |
| `PAIRING` | 配对成功 | `SEARCHING` | 记录对端 `dev_id`、恢复功率、切常态同步字 |
| `PAIRING` | 超时 30 s | `UNPAIRED` | 恢复功率与同步字 |
| `SEARCHING` | 周期发 `BEACON`，对端锁定后开始回报遥测 | `CONNECTED` | 进入常态收发 |
| `CONNECTED` | 连续 N 次无响应 | `SEARCHING` | 继续发 `BEACON` |
| 任意 | 长按解绑 | `UNPAIRED` | 清除配对记录、换回配对同步字 |

### 3.4 RX 侧转移

与 TX 对称，差别是 RX 不主动发 `BEACON`，只监听：

| 起点 | 事件 | 终点 | 动作 |
| --- | --- | --- | --- |
| `UNCONFIGURED` | 写入 `root_key` | `UNPAIRED` | 生成并保存 `dev_id` |
| `UNPAIRED` | 长按按键 | `PAIRING` | 切配对同步字、监听 `PAIR_REQ` |
| `PAIRING` | 配对成功 | `SEARCHING` | 记录对端 `dev_id`、切常态同步字 |
| `SEARCHING` | 收到 `BEACON` | `CONNECTED` | 回响应、进入常态 |
| `CONNECTED` | 超过 T 毫秒无有效包 | `SEARCHING` | 输出失控保护值 |
| 任意 | 长按解绑 | `UNPAIRED` | 清除配对记录 |

失控保护是 `CONNECTED` 之外的一个**输出行为**，不是链路状态：`SEARCHING` 期间
RX 必须持续输出预设的失控值给飞控，不能中断。

### 3.5 会话建立（零回程握手）

TX 周期性在同步信道上发 `BEACON`，携带三样东西：

| 内容 | 作用 |
| --- | --- |
| `nonce_t` | 本次会话的随机数 |
| 跳频信息 | 当前 FHSS 索引，RX 据此对齐跳频 |
| profile | 速率档、tag 开关、加密开关 |

RX 收到后：

1. 校验 `nonce_t` 不是已处理过的旧值（拒绝重放）。
2. 算 `session_key = KDF(pair_key, "sess", nonce_t)`。
3. 按 profile 重配射频（速率、同步字）。
4. 进入 `CONNECTED`，序列号从 0 起，此后收发一律用 `session_key`。

**不需要任何回程确认。** 理由：

- 密钥本身不参与协商，`nonce_t` 是公开值，单向广播足够。
- "TX 是否知道 RX 收到了"本来就靠后续遥测判断，加一次显式 ACK 并不改变这一点。
- RX 比 TX 晚开机时，等下一个 `BEACON` 即可——周期性发送天然解决重新入网。

`nonce_t` 在 TX 每次重启或重建链路时重新随机生成，因此每次会话的密钥都不同。
RX 记住最近接受的 `nonce_t`，重复的丢弃。

已知弱点：攻击者若能重放一个旧 `BEACON`，可把 RX 拉到错误的会话密钥上，
造成一个 `BEACON` 周期长度的中断。下一帧真实 `BEACON` 到达即恢复。
判定为可接受；要消除需要给 `BEACON` 加单调的会话序号。

## 4. 分时结构（草案）

单颗半双工射频要在两个频段间分时，用 RAC 的优先级机制：

| 链路 | RAC 优先级 | 调度方式 |
| --- | --- | --- |
| 控制链路 | `RAC_HIGH_PRIORITY` | 固定周期（如 150 Hz），`SCHEDULED` |
| 数据链路 | `RAC_MEDIUM_PRIORITY` | 控制链路空出来的时隙，`ASAP` |

一个控制周期（6.67 ms @ 150 Hz）的粗略安排：

1. sub-GHz：TX 发 `RC` 帧
2. sub-GHz：TX 转收，等 `TLM` 窗口
3. 2.4G：数据链路在剩余时隙里收发 `DATA_UP` / `DATA_DOWN`

数据链路每次能拿到多少时间，取决于控制帧的空口长度与切换开销，
**必须实测后才能定**，参考 [design.md](design.md) 第 4 节的预算。

## 5. 决策记录

### 已定

| 编号 | 决策点 | 选定 |
| --- | --- | --- |
| D1 | 包过滤 | 同步字硬件过滤，3 个槽的分配见 1.2 |
| D2 | 完整性 | 硬件 CRC + 4 B tag |
| D3 | 安全属性来源 | 由 profile 决定，TX 在 `BEACON` 里声明 |
| D4 | 序列号 | 每会话重置，起点为 0 |
| D5 | 分片 | 单个 `MORE` 位，顺序号复用 `seq` |
| D6 | 建链 | 零回程握手，`BEACON` 携带 `nonce_t` |
| D7 | header 布局 | 6 位类型 + 2 位标志 |

### 待定

1. `seq` 宽度（2 B 是否够）与会话内的回绕处理。
2. 控制链路的帧率与 RC 通道编码（通道数与位宽）。
3. 分片与重组的规则：`MORE` 位语义、超时、乱序处理。
4. `CONFIG` 类型要协商什么，是否真的需要。
5. 数据链路默认 profile（best-effort 还是 ARQ）。
6. 前导码与同步字长度按速率档的取值。
7. 各超时参数：建链超时、失联判定、配对窗口。
8. 失控保护值的来源（飞控下发还是本地配置）。
9. `BEACON` 的发送周期，以及它与控制帧的复用方式。
